# 문제 생성은 어떻게 동작하는가

> 설계 논의(2026-07-28~30)를 정리한 해설 문서. 계약·컴포넌트 상세는
> [스펙](superpowers/specs/2026-07-28-llm-wiki-quiz-generation-design.md) 참조.
> 이 문서는 "왜 이렇게 만들었고, 문제 하나가 어떻게 태어나는가"를 설명한다.

> **후보 JSON 계약(스펙 4.3) 개정 이력** — 스펙 문서는 날짜가 붙은 그 시점의
> 기록이라 사후 고치지 않는다. 그 뒤 바뀐 계약은 여기에 적고, 집행되는 정본은
> 언제나 `question-gen/scripts/validate_candidates.py`(업로드 직전 게이트)다.
>
> | 시점 | 변경 | 비고 |
> |---|---|---|
> | v2 | `subject`(주제 축) 추가 | optional — 부재는 경고, 있는데 틀리면 실패 |
> | v3 (2026-09-03) | `bqReward` 추가 | **필수**. `pointReward`와 나란한 두 번째 보상 축으로, 값은 `scoring.yaml`의 `bq` 표가 난이도로 결정한다. BE의 `quizzes.score` → `point`/`bq` 분리와 짝을 이룬다 |

## 1. 목표: 쇼츠처럼 넘기는 퀴즈

만들려는 것은 시험지가 아니라 **피드**다 — 탭 한 번으로 즉답하고 다음으로 넘기는
쇼츠형 퀴즈. 그래서 형식 제약이 세다:

- **O/X, 2지선다, 4지선다만.** 주관식 없음. 질문은 짧게, 보기는 즉시 판단 가능하게
- 매일 새 문제가 나와야 하고, 유형이 다양해야 지겹지 않다

여기서 첫 번째 문제가 생긴다: *흥미로운 문제 수천~수만 개를 사람이 기획할 수는 없다.*

## 2. 핵심 아이디어: 문제는 뽑는 게 아니라 곱한다

해법은 **질문 템플릿 카탈로그 × 데이터 바인딩**이다.

```
템플릿 1개:  "올해 {팀A} vs {팀B} 상대전적, 우위는?"
          →  팀 조합 45개 × 매일 갱신되는 전적  =  수천 문제
템플릿 1개:  "{선수}의 별명 '{밈}'의 유래는?"
          →  위키의 밈 항목 수백 개              =  수백 문제

템플릿 34개 × 엔티티 조합  =  수만 개의 문제 공간
```

쇼츠가 무한히 넘겨져도 안 지겨운 이유가 "콘텐츠 수만 개를 사람이 만들어서"가 아니라
"포맷 수십 개 × 소재 무한 + 피드백 루프"인 것과 같은 구조다.

템플릿은 [`question-gen/config/question-templates.yaml`](../question-gen/config/question-templates.yaml)에
있다. 각 템플릿은 문구가 아니라 **의도(intent)와 재료(needs)** 를 정의하고, 실제 문구는
LLM이 매번 자유롭게 쓴다. 그래서 같은 템플릿이라도 문제가 늘 조금씩 다르다.

## 3. 재료는 어디서 오나

| 재료 | 원천 | 담기는 곳 |
|---|---|---|
| 경기 결과·일정·라인업 | py-collector가 네이버/KBO에서 수집 → 운영 DB → envelope | S3 `question-source/` |
| 시즌 통계(순위·상대전적·연승) | 경기 봉투를 스크립트로 결정적 집계 (LLM 미사용) | S3 `wiki/stats/` |
| 시즌 스탯 순위(타율·ERA 등)·역대 기록·마일스톤 임박 | **KBO 공식 기록실** 페이지를 py-collector가 일 1회 스냅샷 | S3 `kbo-records/` → `wiki/stats/` |
| 선수 밈·별명·커리어 서사 | **validation 통과** 커뮤니티 글(욕설 검열 + 야구 무관 이슈 배제) + memes.yaml 시드를 위키 빌더(LLM)가 병합 — 원문 직접 소비 금지 | S3 `wiki/players/*.md` |
| 선수 간 관계(밈 공유·커리어 교차) | 위키 front-matter를 컴파일한 경량 그래프 | S3 `wiki/graph.json` |
| 지금 뜨는 화제 | **정제 게시글**에서 화제 토픽 추출 (논란·사건 토픽 제외) | S3 `wiki/stats/trending.md` |

핵심 원칙 두 가지:
- **사실 데이터의 자연어화에 LLM을 쓰지 않는다.** 통계·기록은 스크립트가 집계한다(환각 방지).
  LLM은 서사(밈·여론) 병합과 문제 문구 작성에만 쓴다.
- **퀴즈 생성기는 S3만 읽는다.** DB 접근 없음 — 필요한 데이터는 전부 수집기가 S3에 미리 놓는다.

## 4. 문제 하나가 태어나는 과정

매일 아침 퀴즈 생성기(Claude Code 클라우드 루틴)가 돈다. 먼저 전처리로 `wiki/stats/`
시즌 요약을 오늘 기준으로 재집계(결정적 스크립트)한 뒤, 문제마다 3단계를 거친다.
H2H_SEASON_RECORD 템플릿 하나를 따라가 보자:

```
① 템플릿 선택
   오늘 일정: LG vs 두산.  출제 이력을 보니 어제 이 템플릿 안 씀.
   trending.md를 보니 마침 잠실 라이벌전이 화제.  → 채택

② 데이터 바인딩
   템플릿의 needs: [stats.head_to_head]
   → wiki/stats에서 올해 LG-두산 전적 로드: "LG 7승 4패 우위"

③ 문구 생성 (LLM)
   → 질문: "올 시즌 잠실 라이벌전, 지금까지 우위를 점한 팀은?"
     보기: [LG 트윈스 / 두산 베어스]   정답: LG
     evidence: { source: "wiki/stats/h2h.md", quote: "LG 7-4 두산" }
```

이어서 같은 잡 안에서 **검증 패스**가 돈다:
1. evidence 없는 지식 문제 → 폐기 (환각 차단)
2. 최근 7일 중복·같은 템플릿 편중 → 폐기
3. 안전 필터: 비하·사건·사생활 언급 → 폐기
4. 형식 검사: 보기 2개 또는 4개가 아니면 → 폐기
5. 난이도 산정 → 보상 두 축(`pointReward`·`bqReward`)을 난이도로 결정
   (값은 [`question-gen/config/scoring.yaml`](../question-gen/config/scoring.yaml)의
   `points`·`bq` 표가 정본 — 코드·프롬프트 어디에도 숫자를 복사해 두지 않는다)

통과한 문제만 `quiz-candidates/{날짜}/*.json`으로 S3에 적재되고, BE가 가져가
서비스에 내보낸다. 모든 문제에는 `templateId`가 찍혀 있어 나중에 "어느 유형이
잘 먹히나"를 추적할 수 있다.

## 5. 하지 않는 것 (정책)

- **사건사고는 문제로 만들지 않는다.** 위키에 기록은 하되(선수 맥락 이해용) 퀴즈
  소스로는 금지. 음주운전·폭행·사생활 소재는 명예훼손·2차 가해 리스크
- **정확한 수치는 묻지 않는다** (역대·현역 기록). 현역 선수 통산 기록은 매일 변하므로
  "누가 1위인가", "누가 최초 달성했나" 같은 순위·달성형으로만
- **정산 못 하는 예측은 내지 않는다.** 운영 DB에 스코어와 투수 W/L/S/H밖에 없으므로
  예측 퀴즈는 승패·득점·점수차·투수 decision으로 판정 가능한 것만. "6이닝 이상
  던질까?" 류는 데이터가 생기기 전까지 금지
- **나무위키를 복사하지 않는다.** CC BY-NC-SA(비영리) 라이선스. 기록 사실 자체는
  저작권이 없으므로 KBO 공식 기록실을 원천으로 자체 구성한다

## 6. 품질이 나쁘면 무엇을 고치나

이 구조의 요점: **품질 개선이 전부 파일 편집이다. 모델 학습이 아니다.**

| 증상 | 고치는 곳 |
|---|---|
| 사실이 틀렸다 | 검증 규칙 추가 |
| 재미없다 | 템플릿 삭제 또는 intent 구체화 |
| 문구가 어색하다 | 프롬프트에 좋은/나쁜 사례 추가 |
| 오답이 티 난다 | 템플릿의 distractor 전략 수정 |
| 반복된다 | 편중 검사 강화 |

역할 분담은 이렇게 정했다:
- **템플릿·사례집·프롬프트를 만드는 것은 전부 AI.** 초안 34개도 AI가 썼고,
  신규 템플릿도 루틴이 제안한다
- **사람은 거부권만 갖는다.** 제안된 템플릿 승인/거부, 별로인 문제에 대한 한 줄
  피드백("이런 식은 별로") — 그게 전부. 단, 카탈로그 추가에 대한 사람 승인은
  유지한다. 카탈로그가 안전 규칙·정산 제약이 집행되는 유일한 통제면이기 때문
- **사례집은 자동 갱신.** 루틴이 자기 출제물을 스스로 채점해 good/bad 사례집을
  유지하고, 그것이 다음 실행의 few-shot이 된다
- **유저가 생기면** templateId별 스킵률·정답률이 쌓여 템플릿 가중치 조정이
  데이터로 굴러간다 (2차 단계)

## 7. 용어 (참고)

이 방식은 학술적으로 **템플릿 통제형 자동 문제 생성(AQG)** 에 해당한다. 그래프
관계에서 문제를 만드는 부분은 KGQG(Knowledge Graph Question Generation),
오답 보기 생성은 distractor generation이라 부른다. 구현에 ML 지식은 필요 없다 —
모델 학습·임베딩·벡터스토어가 전부 없는 설계다.
