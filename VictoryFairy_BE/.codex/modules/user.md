# user 모듈

> user 작업 시에만 로드되는 슬림 컨텍스트. (공통: `com.skhynix` 독립 앱, `:common`=ApiResponse/BusinessException/ErrorCode, `:domain`=엔티티/리포지토리, MySQL+spring-dotenv, prod `ddl-auto`는 앱마다 다름 — user=`update`, quiz=`none`)

## 책임
JWT 기반 인증/인가 + 회원 탈퇴 + 이메일 인증(가입 선행조건) + 프로필 수정(닉네임/비밀번호) + **만료 데이터 정리**(탈퇴 30일 경과 계정 하드 삭제, 매일 03:00 KST — 이 모듈 최초의 `@EnableScheduling`). signup·login·refresh·logout·withdraw·email 인증·nickname/password 수정. **포트 8080.**

## 핵심 클래스 (`user/src/main/java/com/skhynix/...`)
- `AuthController` → `/api/auth/*`
- `AuthService` — 가입/로그인/재발급/로그아웃 로직. **가입 트랜잭션이 `UserBq`(`:domain`) 행도 함께 만든다**(`bq_score=0`, 계정 저장과 원자적 — signup 요청·응답 계약은 불변). `issueTokens(UserAccount, LocalDateTime)`는 토큰 재발급 절차(기존 유효 refresh 만료→새 쌍 발급)를 재사용하려는 호출자(`UserProfileEditService`)를 위해 연 public 오버로드 — 무인자 `issueTokens()`는 종전처럼 `LocalDateTime.now()`를 그대로 쓰고 login·reissue 동작은 불변
- `account.controller.UserAccountController` → `/api/users/*` · `account.service.UserAccountService` — 탈퇴(soft delete) 전용. `AuthService`에 얹지 않은 이유: 탈퇴는 토큰을 **만들지 않고 지우기만** 해서 `AuthService` 협력자 5개 중 `PasswordEncoder`/`JwtTokenProvider`/`UserRepository` 3개가 불필요
- `account.service.UserProfileService`(클래스 레벨 `@Transactional(readOnly = true)`, 쓰기 경로 없음) — 내 프로필 조회 전용. `UserAccountService`(탈퇴)에 합치지 않은 이유는 같은 협력자 필요 범위 불일치 논리다: 탈퇴는 `UserRefreshTokenRepository`를 쓰고 조회는 안 쓰며, 조회는 `UserSupportTeamRepository`·`UserBqRepository`·`SupportService`를 쓰고 탈퇴는 안 쓴다(공유는 `UserAccountRepository` 하나뿐). **협력자에 `SupportService`가 있어 순수 리포지토리 조합이 아니다** — 응원 선수 목록은 `supportService.currentSupportedPlayers(userAccountId)`로 재사용해 로직을 복제하지 않는다(호출 대상이 `readOnly`라 조회 전용 성격은 유지). "조회가 행을 만들지 않는다"는 계약(USER-ME-20)을 쓰기 경로 없는 클래스로도 표현한다. `account.dto.UserAccountResponse`(record `nickname`/`supportTeam`/`supportPlayers`/`point`/`bqScore` — 구단은 `team.dto.TeamResponse`, 응원 선수는 `player.dto.PlayerResponse` 재사용(둘 다 전용 DTO를 새로 안 만든 것과 같은 판단), `supportPlayers`는 없으면 `null`이 아니라 빈 배열)
- `account.service.UserProfileEditService`(클래스 레벨 `@Transactional`, 쓰기 경로 2개: 닉네임·비밀번호 수정) — `UserProfileService`(조회 전용)에 얹지 않은 이유: 쓰기 경로가 섞이면 "조회는 행을 만들지 않는다" 계약이 클래스 모양으로 안 보인다. `UserAccountService`(탈퇴)와도 합치지 않았다 — 탈퇴는 `UserRefreshTokenRepository`를 직접 쓰고 여기는 `AuthService.issueTokens`에 위임해 안 쓰며, 여기는 `PasswordEncoder`·`AuthService`·`Clock`을 쓰고 탈퇴는 안 쓴다(공유는 `UserAccountRepository` 하나). 닉네임 판정은 ①길이→②문자→③현재 값과 동일→④타 계정 점유(`existsByNickname`)→⑤쿨다운(마지막이라 **쿨다운 중인 계정이 이미 점유된 닉네임을 요청하면 429가 아니라 409**), 성공 시 `UserAccount.changeNickname`이 닉네임 교체와 시각 기록을 한 전이로 묶는다. 비밀번호는 현재 비밀번호 일치→신·구 동일 순, **쿨다운 없음**(의도적 비대칭 — 유출 대응 수단을 잠그지 않기 위함 + 후속 access 토큰 무효화 작업의 트리거를 봉인하지 않기 위함), 성공 시 `authService.issueTokens(account, LocalDateTime.now(clock))`로 기존 refresh 전량 만료 + 재발급하며, **변경 이전에 발급된 access·refresh 토큰도 즉시 무효화된다**(`account.changePassword(encoded, Instant.now().getEpochSecond())`가 `issueTokens` 호출 **직전**에 기준 시각을 기록 — 순서를 뒤집으면 방금 발급한 토큰이 스스로 무효화된다. 이 한 줄만 `Clock` 빈이 아니라 `Instant.now()`를 쓰는 이유·차단 지점 상세는 아래 무효화 항목 참고). DTO는 `account.dto.NicknameUpdateRequest`/`PasswordUpdateRequest`(record, `@ValidNickname`/`@ValidPassword` 단일 검증만 걸고 겹쳐 걸지 않음 — `currentPassword`는 검증 애노테이션 없이 null 허용, 서비스가 "불일치"로 흡수), `account.dto.NicknameChangeCooldownResponse`(record `nextChangeableAt` 하나, `BusinessDataException(NICKNAME_CHANGE_COOLDOWN, ...)`으로 실리는 이 저장소 **첫 실패 응답 data** — `ISO_OFFSET_DATE_TIME` 대신 `yyyy-MM-dd'T'HH:mm:ssXXX` 포맷을 쓴다, 전자는 초가 0이면 `:00`을 생략해 값 자릿수가 시각마다 달라진다)
- `SecurityConfig` — stateless + JWT 필터 통합 + `RestAuthenticationEntryPoint` 등록(401). `securityFilterChain(HttpSecurity, JwtTokenProvider, UserAccountRepository, ObjectMapper)`. **`JwtTokenProvider`/`JwtAuthenticationFilter`/`RestAuthenticationEntryPoint`/`GlobalExceptionHandler`는 `web-support` 모듈 소속**(`com.skhynix.websupport.*`)이라 컴포넌트 스캔 밖 — `UserApplication`이 `@Import({JwtVerificationConfig.class, GlobalExceptionHandler.class})`로 명시 등록한다
- `auth.policy.PasswordPolicy` — 비밀번호 정책(길이 8~12, 영문+숫자+특수문자)의 **단일 출처**. `findViolation()`을 signup 검증과 `/password/validate`가 공유
- `auth.policy.ValidPassword`/`PasswordValidator` — `PasswordPolicy.findViolation()`에 위임하는 커스텀 제약
- `auth.policy.NicknamePolicy` — 닉네임 정책(허용 문자 화이트리스트 `[가-힣ㄱ-ㅎㅏ-ㅣa-zA-Z0-9]`, 길이 1~10, 위반 우선순위 길이→문자)의 **단일 출처**. `PasswordPolicy`와 동일 구조. `findViolation()`을 signup 검증과 `/nickname/validate`가 공유(중복은 여기서 판정하지 않음). ⚠ **이 화이트리스트에 괄호가 없다는 사실이 `(알수없음)` 예약 닉네임(만료 데이터 정리의 더미 계정, `cleanup.policy.UnknownAccountPolicy`)의 사칭 방지 근거다** — `nickname`엔 DB UNIQUE가 없어 막는 건 중복 검사가 아니라 이 문자 정책뿐이다. 허용 문자를 넓히는 변경(이모지 등 흔한 요청)은 이 보장을 조용히 깬다
- `auth.policy.ValidNickname`/`NicknameValidator` — `ValidPassword`/`PasswordValidator`를 그대로 미러링해 `NicknamePolicy.findViolation()`에 위임하는 커스텀 제약
- `auth.policy.NicknameChangeCooldownPolicy` — 닉네임 재변경 간격(30일, `COOLDOWN_DAYS`가 단일 출처) 판정. `NicknamePolicy`에 합치지 않은 이유: 저쪽은 문자열만으로 판정이 끝나 회원가입도 공유하지만, 이쪽은 계정의 마지막 변경 시각(`UserAccount.nicknameChangedAt`, `LocalDateTime`)이 있어야 판정 가능해 수정 경로 전용이다. **판정은 `LocalDateTime` 끼리의 비교다**(2026-08-17 `Instant`/epoch 초에서 전환) — 존이 없는 값이라 "같은 `Clock`(Asia/Seoul)에서 읽힌 벽시계"라는 전제가 호출자 책임이고, `LocalDateTime.now()`(시스템 기본 존)를 섞으면 `TZ` 환경변수가 없거나 다른 파드에서 9시간 어긋난다(2026-08-18 실측으로 운영 파드는 지금 `TZ=Asia/Seoul`이라 당장은 안 어긋나지만, 그 설정 하나에 기대지 않는 것이 `Clock` 빈을 쓰는 이유다)
- `auth.service.EmailVerificationService` — 이메일 소유 검증 정책 판정(발송 쿨다운/시도 5회 한도/1회용 소비). 실제 저장은 `EmailVerificationStore`(포트)에, 발송은 `EmailSender`(포트)에 위임
- `auth.store.EmailVerificationStore`(포트) / `RedisEmailVerificationStore`(Redis 구현) — `StringRedisTemplate` 기반으로 전 메서드 완성 구현(런타임 검증 통과)
- `auth.email.EmailSender`(포트) — `SmtpEmailSender`(`@Profile("prod")`, `JavaMailSender` 실발송) / `LogEmailSender`(`@Profile("!prod")`, 로그로만 대체 — dev/test 실메일 미발송)
- DTO는 전부 **record**: `SignupRequest`, `LoginRequest`, `TokenRequest/Response`, `PasswordValidationRequest/Response`, `NicknameValidationRequest/Response`, `EmailSendCodeRequest`, `EmailVerifyRequest`. signup은 `ResponseEntity<Boolean>` 반환(미사용이던 `SignupResponse`는 삭제됨)
- `player.controller.PlayerController`(`/players`, GET만, 쿼리 파라미터 `teamId`·`name` 둘 다 선택) → `player.service.PlayerService`(클래스 레벨 `@Transactional(readOnly = true)`, 협력자 2개 — `PlayerRepository` + `UserSupportTeamRepository`, 시그니처 `getPlayers(userAccountId, teamId, name)`) → `PlayerRepository` 의 **2×2 조합 메서드 4개**: `findAllByOrderByNameAsc()` / `findAllByTeam_IdOrderByNameAsc(teamId)` / `findAllByNameContainingOrderByNameAsc(name)` / `findAllByTeam_IdAndNameContainingOrderByNameAsc(teamId, name)`. **`name` 은 prefix 가 아니라 contains**(`LIKE '%name%'`) — 초안 코드가 `StartingWith` 였다가 2026-08-03 결정 6으로 뒤집힌 자리다. `IgnoreCase` 는 MySQL `_ci` 콜레이션이 이미 흡수하므로 붙이지 않는다. **빈 문자열·공백 검색어를 "검색어 없음"으로 접는 주체는 서비스 한 곳뿐**(`?name=` 을 Spring 이 `null` 이 아니라 `""` 로 넘기므로 필요, 컨트롤러는 받은 값을 그대로 전달). `player.dto.PlayerResponse`(record `teamId`+`teamName`+`playerId`+`playerName`+`playerNumber`+`playerPosition`, `kboPlayerId`·`average`는 미노출 — 전자는 py-collector 소유 자연키. 2026-08-06 에 `id`+`name` 에서 바뀐 **파괴적 변경**이다). **`playerNumber`·`playerPosition` 은 nullable 이고 대체값 없이 `null` 로 나간다** — `positionGroup` 이 null 인 행에서 enum 을 곧바로 `toString()` 하면 NPE 라 `from()` 이 null 검사를 낀다. 구단을 담게 되면서 LAZY 인 `Player.team` 이 변환 시점에 초기화된다 — **변환은 반드시 트랜잭션 안**이어야 하고, 1차 캐시가 흡수해도 서로 다른 구단 수(최대 10)만큼 추가 SELECT 가 붙는다(**`PlayerRepository` 자체 4종**에는 fetch join 이 아직 없다 — 응원 선수 조회용 fetch join 은 `UserSupportPlayerRepository` 쪽에 별도로 있다, 아래 참고). **DTO 는 `:domain` 이 아니라 앱 모듈(`user.player.dto`)에 둔다** — API 계약을 공유 모듈에 두면 quiz 까지 끌려간다(초안이 `domain.player.entity` 에 뒀다가 옮긴 자리). 계약은 `docs/requirements/user/player-list.md`(USER-PL-1~16) + `player-lookup-team-fallback.md`(USER-PLF-1~21, 응원 구단 오버라이딩) — 둘 다 구현 후 사후 작성이다
- `support.controller.SupportController`(`/support/**`, **인증 필수**) → `support.service.SupportService`(클래스 레벨 `@Transactional`, 조회 헬퍼만 `readOnly`). 요구사항 `docs/requirements/user/support-selection.md`(USER-SP-1~46, 30~37은 2026-08-06 응원 선수 4명 상한, 38~46은 같은 날 계정 행 락). **domain 이 "아무도 강제하지 않는 정책"이라 경고했던 구단 1개 정책의 강제 주체**다. 지켜야 할 불변식 5개: ①`oppose is null` 인 구단 행은 계정당 1개 ②응원 선수는 응원 구단 소속 ③구단이 실제로 바뀌면 응원 선수 전원 자동 취소(②의 귀결) ④취소는 삭제가 아니라 `oppose` 전이 ⑤**활성 응원 선수는 4명을 넘지 않는다**(`MAX_SUPPORT_PLAYERS` 상수가 단일 출처, `addPlayers`만 강제하고 `opposePlayers`는 무관, 판정은 활성 id ∪ 요청 distinct id 의 합집합 크기 — 초과 시 부분 반영 없이 요청 전체 거부, 기존 초과 데이터는 잘라내지 않음). **쓰기 경로 3개(`selectTeam`·`addPlayers`·`opposePlayers`) 모두 첫 줄에서 `lockAccount(userAccountId)`를 호출한다**(빈 `playerIds` 요청도 예외 없이 락부터 — "쓰기 경로는 항상 락부터"). `lockAccount`는 `UserAccountRepository.findWithLockById`(계정 PK 비관적 쓰기 락)를 감싸고, 계정이 없으면 `UNAUTHENTICATED`(이 예외를 던지는 세 번째 지점, 기존은 `UserProfileService`·`UserAccountService`). **읽기 경로 `currentSupportedPlayers`(`GET /me`가 재사용)에는 락이 없다** — 조회끼리 서로 막지 않기 위한 계약. 상한(4명)의 실제 강제 지점은 "판정만"이 아니라 "판정 + 계정 락"이다 — 락을 떼면 판정 코드를 그대로 둬도 뚫린다. 요청 DTO 는 `support.dto.SupportTeamRequest`/`SupportPlayersRequest`(둘 다 record), 응답은 **기존 `TeamResponse`/`PlayerResponse` 를 재사용**(응원 전용 DTO 를 새로 만들지 않았다). 응원 선수 응답은 `UserSupportPlayerRepository.findAllActiveWithPlayerAndTeam`(선수+구단 fetch join 1쿼리)로 만든다. ⚠ 재사용이라 **`PlayerResponse` 를 고치면 `/players`·응원 API·`/me`(`supportPlayers`, `UserProfileService`가 재사용) 세 곳이 함께 바뀐다** — 2026-08-06 항목 키 교체가 실제로 그렇게 번졌고, 같은 날 `/me`가 세 번째 소비처로 늘었다

## 주의 / 컨벤션
- 토큰 claim `type: access|refresh` → `isRefreshToken()`으로 구분
- **토큰 subject = `UserAccount.uid`(UUID v4). 내부 PK `id`는 claim 어디에도 싣지 않는다** — JWT payload는 서명만 되고 암호화는 안 돼 base64 디코드로 누구나 읽을 수 있으므로, id를 claim에 넣으면 uid로 감추는 의미가 사라진다. 이후에도 지켜야 할 정책.
- `JwtAuthenticationFilter`가 요청마다 `UserAccountRepository.findActiveAuthByUid(uid)`(`:domain`, `exit_at is null` 조건 포함, `Optional<Long>`이 아니라 `Optional<ActiveAccountView>`{id, passwordChangedEpochSecond} 반환)로 uid→id를 해석해 **principal은 여전히 `Long` id**(내부 계약 불변). uid로 못 찾으면(미존재 또는 탈퇴) `SecurityContext`를 비운 채 그대로 체인 통과(예외 없음) → `anyRequest().authenticated()`가 401로 떨어뜨림. **찾았어도 토큰의 `iat`가 그 계정의 `passwordChangedEpochSecond`보다 앞선 초면 마찬가지로 principal을 안 채운다**(`ActiveAccountView.acceptsTokenIssuedAt`, 아래 무효화 항목 참고) — 예외 없이 통과라 인증 필수 경로는 기존 미인증과 문자 그대로 같은 401, `permitAll`이면서 토큰을 읽는 `/api/players`는 헤더 없는 요청과 동일하게 200. 요청당 조회 1회는 id를 숨기는 대가로 의도된 비용이며(기준 시각을 같은 조회에 얹어 추가 조회는 없음) 캐시는 없음
- **탈퇴 계정 차단 지점은 3곳**: 필터(`findActiveAuthByUid`) · `AuthService.login`(`findByUser_EmailAndExitAtIsNull`) · `AuthService.reissue`(`account.isWithdrawn()`). `login`·`refresh`는 `permitAll`이라 필터를 안 타서 각자 판정이 필요하다. `reissue`의 탈퇴 검사는 이중 방어가 아니라 **레이스 방어**다 — 탈퇴가 refresh 토큰을 전부 만료시켜 정상 경로에선 만료 검사에 먼저 걸리지만, READ_COMMITTED에서 login 트랜잭션이 탈퇴 커밋 전 계정을 읽고 `expireValidTokens` 이후에 새 토큰을 INSERT하면 탈퇴 계정에 유효 토큰이 남을 수 있다. `account`는 `issueTokens`가 어차피 초기화해 추가 조회는 0회
- **비밀번호 변경 토큰 무효화(2026-08-17, `docs/requirements/user/access-token-invalidation.md` USER-ATI-1~22)**: `UserAccount.passwordChangedEpochSecond`(epoch 초, `:domain`)를 기준으로 그보다 **앞선 초**에 발급된 토큰을 거절한다(같은 초는 유효 — `iat`가 초 단위로 내려오므로 `>`로 바꾸면 비밀번호 변경 응답으로 방금 준 새 토큰이 자기 자신에게 거부된다). 판정 단일 출처는 `UserAccount.acceptsTokenIssuedAt(Long, long)`(static). **차단 지점은 2곳**: 필터(`findActiveAuthByUid`가 함께 실어 온 값으로 access 판정, 요청당 조회 증가 없음) · `AuthService.reissue`(`account.acceptsTokenIssuedAt(iat)`, refresh 판정 — 탈퇴 검사 바로 다음 줄, 계정은 이미 로딩돼 있어 추가 조회 0회, 위 탈퇴 레이스 방어와 같은 이유로 만료 검사 뒤에 있어도 필요하다). `reissue`는 이제 **만료·탈퇴·`iat` 대조 3단계**를 통과해야 새 토큰을 받는다. `iat`가 없는 토큰(정상 발급 경로에선 항상 있음)은 `Long.MIN_VALUE`로 흡수해 fail-closed. **로그아웃은 여전히 access 토큰을 죽이지 않는다**(기준 시각을 안 건드림, 최대 3h 그대로) — 이 기능이 닫은 구멍은 "변경 전 access 토큰이 최대 3h 살아남는다"는 것뿐이고, 남는 한계는 변경과 **같은 초**에 있던 이전 토큰이 살아남는 ≤1초 창이다
