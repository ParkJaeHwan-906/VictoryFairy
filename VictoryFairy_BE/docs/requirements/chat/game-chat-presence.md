# 경기 채팅방 접속 인원(presence) 요구사항
> 상태: 승인됨 (2026-10-12) · 모듈: chat · 최종 수정: 2026-10-12

> **개정 2026-10-12 (승인)**: 초안의 미해결 질문 8건을 사용자가 전부 결정했다. 가장 큰 변경은 **종료 시 제거 판정 방식**이다. 초안은 이를 시각 비교로 가정했는데, 사용자는 **방별 소유 파드(instanceId) 기준**으로 정했다. 그래서 소유 키 `chat:presence-owner:{gameId}`가 추가됐다. 생존 시각은 **Redis 서버 시각**으로 기록하고 판정한다(CHAT-PR-30 신설). 이렇게 해서 파드 시계에 의존하는 곳이 없어졌다. 나머지 결정은 다음과 같다. 숫자는 15초 / 45초 / 2초다. REST는 두지 않는다. Redis 장애 시에는 이벤트를 생략한다. 자정 UNLINK 대상에서 제외한다. 형식은 `{"count":N}`이고 본인을 포함한다. QUIZ-CHAT-52는 경기 채팅에 한해 철회했으며, `game-chat.md` 범위 "제외"의 해당 줄을 같은 날 개정했다. 남은 `(가정)`은 없다.

> **개정 2026-10-12 (2차, 승인)**: 구현 테스트에서 문제가 하나 드러났다. presence 키가 소실된 뒤 다음 생존 갱신(최대 15초)이 오기 전까지, 구독자에게 실제보다 작은 값이 나갔다(예: 3 → 0 → 3). PR-10은 만족하지만, PR-23의 "틀린 숫자보다 멈춘 숫자" 취지에 어긋난다. 사용자는 이렇게 결정했다. 집계 값이 **그 파드에 지금 구독 중인 고유 계정 수**보다 작으면 명백히 틀린 값이므로, 그 주기 전송을 생략한다. 구독 직후 초기 값에도 같은 규칙을 적용한다(PR-31 신설). 이때 초기 값을 못 받은 구독자가 다음 유효 주기에 값을 받는 경로가 필요한데, 기존 PR-14(같은 값이면 안 보냄)가 이 경로를 막고 있었다. PR-25의 초기 값 생략에도 같은 구멍이 있었다. 그래서 PR-32를 신설했다. 이 개정으로 PR-10·14·25·26의 문장 또는 인수 기준, 장애 표, 알려진 결과 6, 결정 근거 10을 고쳤다. 파드 로컬 값으로 대신 보내는 폴백은 여전히 없다(전제 7 유지).

## 배경 / 목적
경기 방에 지금 몇 명이 함께 보고 있는지를 화면에 띄운다. 지금 이 값을 낼 수 있는 곳은 `SseEmitterRegistry.count(gameId)` 하나다. 그런데 이 값은 **파드 로컬 연결 수**다. HPA로 게이트웨이 파드가 늘면 파드마다 다른 값이 되고, 어느 파드도 방 전체 인원을 모른다. 그래서 인원은 파드 밖(Redis)에서 방 단위로 모아 세야 한다.

이 문서는 승인된 [`game-chat.md`](game-chat.md)(CHAT-GC-*)와 [`game-chat-likes.md`](game-chat-likes.md)(CHAT-LK-*) **위에 더하는** 계약이다. 인증, SSE 구독, last-one-wins 축출(CHAT-GC-34·35), 하트비트(CHAT-GC-32), 쓰기 풀(CHAT-GC-89·90) 계약은 그대로 전제하며, 여기서 바꾸지 않는다. `game-chat.md` 범위 "제외"에 있던 "참여 인원 노출(QUIZ-CHAT-52 유지)"은 경기 채팅에 한해 이 문서로 대체됐다(2026-10-12 개정).

## 범위
- 포함:
  - 방별 접속 인원의 정의(고유 계정 수)와 파드를 합친 집계
  - 구독 성립·생존 갱신·종료·만료에 따른 인원 반영, 종료 시 소유 파드 판정
  - SSE 이벤트 `presence`: 구독 직후 1회, 이후 값이 바뀔 때. 방별 주기 병합 포함
  - 신규 Redis 키 2종(`chat:presence:{gameId}`·`chat:presence-owner:{gameId}`)의 수명
  - Redis 장애 시 동작, 역할 플래그별 동작, 설정 키
- 제외:
  - **인원 조회 REST** — `GET /chat/rooms`·`GET /chat/rooms/{gameId}` 응답에 인원 필드를 넣지 않는다. 숫자는 구독해야 보인다
  - 접속자 **명단**(닉네임·프로필 목록). 숫자만 낸다
  - 구단별 인원 분해(예: KIA 120 / LG 80)
  - 인원 이력·최고 동시 접속 기록·통계 저장
  - Redis 장애 중의 대체 값(파드 로컬 값 폴백, "집계 불가" 신호)
  - quiz `/rt/chat/**` 쪽 인원(QUIZ-CHAT-52는 quiz에서 그대로 유지 — CHAT-GC-103)
  - 기존 `messages`·`deleted`·`reset`·`likes` 이벤트, 하트비트, 전송·좋아요 계약의 변경

## 확정 전제 (사용자와 합의 완료 — 되묻지 않는다)
1. **인원 = 그 방에 열린 SSE 구독을 가진 계정의 고유 수(userAccountId 기준 distinct)다.** 연결 수가 아니다. 같은 계정이 여러 파드나 여러 기기로 붙어 있어도 1명이다. 인원에는 **구독자 본인이 포함된다.**
2. **집계 저장소는 Redis ZSET `chat:presence:{gameId}`다.** member는 계정 id, score는 마지막 생존 시각이다. `INCR`/`DECR` 카운터는 쓰지 않는다. 파드가 크래시하면 `DECR`이 영영 오지 않아 오차가 영구히 쌓이기 때문이다. ZSET은 만료 창이 지나면 스스로 실제 값으로 돌아온다.
3. **생존 시각은 Redis 서버 시각으로 기록하고 판정한다**(CHAT-PR-30). 파드 시계는 score 기록에도, 만료 판정에도 쓰지 않는다.
4. **종료 시 제거는 소유권으로 판정한다.** 방마다 "그 계정을 마지막으로 등록한 파드의 instanceId"를 기록한다(`chat:presence-owner:{gameId}`, 계정 id → instanceId). 구독이 끝날 때는 두 조건을 모두 만족해야만 지운다. ① 소유자가 자기 instanceId다. ② 자기 파드에 그 계정의 그 방 구독이 더 없다. 이때 ZSET member와 소유 기록을 **원자적으로** 함께 지운다. 시각 비교는 쓰지 않는다.
   - 등록(구독 성립)은 소유자를 **자기로 덮어쓴다.** 마지막 등록자가 소유자가 된다.
   - 생존 갱신은 **소유자가 없을 때만** 자기를 소유자로 기록한다. 이미 있는 소유자를 빼앗지 않는다.
   - 만료로 member가 걷힐 때는 그 계정의 소유 기록도 함께 지운다.
   - instanceId는 프로세스마다 새로 만들어지는 값(`SseEmitterRegistry.instanceId`)이다. 재시작한 파드는 옛 소유 기록의 주인이 아니다.
5. **숫자**: 생존 갱신은 기존 하트비트 주기 15초(CHAT-GC-32)를 공유한다. 만료 창은 45초, 전달 주기는 2초다. 단 하트비트 스케줄러 스레드가 Redis 왕복으로 붙잡혀서는 안 된다(제약 6).
6. **파드 간 전파는 "각 게이트웨이 파드의 주기 집계"다.** 로컬 구독자가 있는 방마다 2초마다 다음을 한다. 만료 member를 걷고, 인원을 센다. 그 값이 그 파드가 그 방에 마지막으로 보낸 값과 다르면 로컬 구독자에게 보낸다. 새 pub/sub 채널은 두지 않는다(아래 "결정 근거" 1).
7. **Redis 장애 중에는 `presence` 이벤트를 보내지 않고, 화면의 마지막 값을 그대로 둔다.**
8. **presence 키 2종은 자정 정리(CHAT-GC-16) 대상이 아니다.** 쓸 때마다 연장되는 90초 TTL로만 소멸한다. 이것은 모듈 규칙 "방 단위 키를 새로 만들면 `RoomLifecycleJob` 정리 목록에도 추가"의 **의도된 예외**다. 근거는 "기존 정책과의 충돌" 1을 보라.
9. **이벤트 형식은 `event: presence` / `data: {"count":N}`이다.** REST로는 인원을 내지 않는다.

### Redis 키 (확정)

| 키 | 타입 | 쓰는 쪽 | 수명 |
|---|---|---|---|
| `chat:presence:{gameId}` | ZSET (member=계정 id, score=마지막 생존 시각, **Redis 서버 시각** epoch ms) | 게이트웨이 역할 | 쓸 때마다 `EXPIRE 90`(CHAT-PR-20). 자정 UNLINK 대상 아님(CHAT-PR-21) |
| `chat:presence-owner:{gameId}` | HASH (field=계정 id, value=소유 파드 instanceId) | 게이트웨이 역할 | 위와 같음 |

### 설정 키 (확정)

| 키 | 기본값 | 쓰는 곳 |
|---|---|---|
| `chat.presence.expire-seconds` | 45 | CHAT-PR-7 (하트비트 15초 × 3 — 갱신 2번을 놓쳐도 빠지지 않는다) |
| `chat.presence.broadcast-interval-ms` | 2000 | CHAT-PR-12·13 |
| `chat.presence.key-ttl-seconds` | 90 | CHAT-PR-20 (만료 창 × 2) |

생존 갱신 주기는 새 키를 두지 않고 하트비트 15초(CHAT-GC-32)를 그대로 쓴다. 전부 환경변수(relaxed binding, 예 `CHAT_PRESENCE_EXPIRE_SECONDS`)로 덮어쓸 수 있다.

## 프론트 영향 (FE 필독)

| 항목 | 내용 |
|---|---|
| SSE 신규 이벤트 | `event: presence` / `data: {"count":N}`. 구독 직후 1번 오고, 그 뒤에는 값이 바뀔 때만 온다(최대 2초에 1번). **`id:`가 없다** |
| 본인 포함 | 값에 자기 자신이 들어 있다. 혼자 있으면 1이다 |
| REST | 방 목록·상세 응답에는 인원이 없다. 방에 들어가(구독해) 첫 `presence`를 받아야 숫자가 생긴다 |
| 재접속 | 재접속하면 첫 값이 다시 온다. 끊긴 동안의 값을 따로 복구할 필요가 없다 |
| 값이 안 오는 경우 | Redis 장애 때는 프레임이 오지 않는다. 마지막 값을 그대로 보여 주면 된다. 구독 직후 첫 값이 안 왔다면 숫자를 숨기는 것이 맞다 |
| 정확도 | 근사값이다. 비정상으로 끊긴 사람은 최대 약 47초 늦게 빠진다 |
| 구버전 클라이언트 | `presence` 리스너가 없으면 무시된다. 폴리필이 `event` 이름을 보지 않고 모든 `data`를 메시지 배열로 처리한다면 `{"count":N}`을 오해할 수 있다(`likes`와 같은 확인 사항) |

## 알려진 결과 (결함이 아니라 알고 택한 것)
1. **비정상 끊김은 만료 창만큼 늦게 빠진다.** 파드 크래시, 네트워크 단절처럼 서버가 끊김을 모르는 경우다. 서버는 다음 하트비트 쓰기가 실패하거나(CHAT-GC-36) 만료 창이 지나서야 안다. 최악은 `expire-seconds + broadcast-interval-ms`(약 47초)다.
2. **입장·퇴장의 반영은 최대 `broadcast-interval-ms`(2초) 늦다.** 파드마다 주기가 독립이라, 같은 방이라도 파드가 다르면 새 값을 최대 2초 차이로 받는다(PR-18이 수렴을 보장한다).
3. **Kafka 장애로 축출이 전파되지 않으면 소유권 판정이 한 번 틀릴 수 있다.** 같은 계정이 같은 방에서 파드 1(먼저)과 파드 2(나중, 소유자) 양쪽에 구독을 가진 상태라고 하자. 여기서 파드 2 구독이 먼저 끝나면 소유자가 자기라서 지운다. 파드 1 구독은 살아 있는데도 그렇다. 그 계정은 파드 1의 다음 생존 갱신(최대 15초)에 다시 반영되고, 이때 파드 1이 소유자가 된다(PR-6). 정상 상태에서는 last-one-wins(CHAT-GC-34)로 한 계정의 구독이 전체에서 1개라 이 일이 생기지 않는다.
4. **Kafka 장애 중에는 같은 계정이 서로 다른 두 방에 동시에 집계될 수 있다.** 전제 1의 중복 제거는 방 안에서만 성립한다.
5. **어제 방의 열린 스트림은 자정 뒤에도 인원을 받는다**(PR-22). 새 구독은 404(CHAT-GC-31)이므로 그 값은 줄어들기만 한다.

6. **PR-31은 "자기 파드 몫이 빠진" 틀린 값만 거른다. 다른 파드 몫만 줄어든 틀린 값은 걸러지지 않는다.** 판정 기준이 그 파드가 직접 아는 하한(로컬 고유 계정 수)뿐이기 때문이다. 예를 들어 실제 300명(파드 1에 120, 파드 2에 180)인 방에서 키가 소실된 뒤 파드 1만 먼저 생존 갱신을 마쳤다고 하자. 그러면 집계 값 120은 파드 1의 로컬 수 이상이라 통과한다. 결과적으로 파드 1 구독자는 파드 2의 다음 생존 갱신 전까지(최대 15초) 120을 보고, 그 뒤 300으로 돌아온다. 키 소실·Redis 데이터 손실 같은 드문 장애에서만 생기며, 15초 안에 수렴한다.

## 결정 근거 (해소된 질문 — 다시 논의하지 않기 위해)
1. **전파는 주기 집계(pub/sub 아님), 주기 2초.** 인원은 정확한 순간값보다 수렴하는 값이 중요하다. 주기 집계는 크래시 파드의 유령 member 청소, Redis 장애 뒤 복구, 입장 폭주 병합(O(N²) 방송 방지)을 "다음 주기"라는 하나의 장치로 해결한다. pub/sub 변경 신호는 지연이 짧은 대신, 구독 루프·재구독·유실 보정이 필요하다. 게다가 유령 청소용 주기 처리도 결국 따로 필요해 장치가 둘이 된다. KBO는 하루 최대 5경기라 파드당 주기 비용이 작다.
2. **종료 시 즉시 제거 + 소유권 판정(초안 C안의 변형).** 만료로만 빼면 퇴장이 47초 늦게 보인다. 무조건 즉시 빼면 다른 파드로의 재접속(축출 순서 "새 등록 → 옛 종료") 때 최대 15초간 1명이 빠져 보인다. 판정 기준은 시각 비교가 아니라 **소유 파드 instanceId**다. 시각 비교는 파드 시계 일관성에 기대고, 같은 밀리초의 동률을 처리할 방법이 없다. member를 `계정:인스턴스`로 두는 안(초안 D)도 탈락했다. 이 안은 `ZCARD`로 고유 계정 수가 나오지 않아, 주기마다 member 전체를 읽어 중복을 빼야 하기 때문이다.
3. **생존 시각은 Redis 서버 시각.** 만료 판정에는 여전히 시각이 필요하다. 그래서 그 시각의 출처를 하나(Redis)로 고정해 파드 시계 의존을 없앴다.
4. **생존 갱신 15초(하트비트 공유) / 만료 45초.** 갱신 2번을 놓쳐도 빠지지 않는다. 새 타이머를 두지 않는다.
5. **REST 없음.** 목록의 "Redis를 보지 않는다"(CHAT-GC-26)와 상세의 장애 응답을 건드리지 않는다.
6. **Redis 장애 시 이벤트 생략.** 파드 로컬 값으로 폴백하면 다중 파드에서 값이 갑자기 작아졌다가 튄다. 틀린 숫자보다 멈춘 숫자가 낫다.
7. **자정 UNLINK 제외, 90초 롤링 TTL.** "기존 정책과의 충돌" 1.
8. **`{"count":N}`, 본인 포함.** 객체 형식은 `deleted`의 `{"msgId":n}`과 결이 같고 필드 확장이 쉽다. 본인을 포함하면 같은 방 구독자 모두에게 같은 값을 보낼 수 있다.
9. **QUIZ-CHAT-52 철회(경기 채팅 한정).** `game-chat.md` 범위 "제외"를 같은 날 개정했다. quiz는 유지한다.
10. **(2차 개정) 로컬 고유 계정 수보다 작은 집계 값은 생략(PR-31), 초기 값 포함.** 그 파드에 지금 구독 중인 계정은 확실히 방에 있으므로, 그보다 작은 집계는 명백히 틀린 값이다. 이 값을 보내면 PR-23의 "틀린 숫자보다 멈춘 숫자" 원칙을 어긴다. 로컬 값을 대신 보내지 않는 이유는 결정 6과 같다. 초기 값에도 같은 규칙을 적용해 일관성을 지켰다. 생략된 초기 값은 PR-25와 같은 방식으로 다음 유효 주기에 보낸다(PR-32). 다른 파드 몫의 축소는 거를 기준이 없어 알려진 결과 6으로 수용했다.

## 기존 정책과의 충돌 / 계약 성립 제약 (구현 방법 지시가 아니라 지켜야 할 사실)
1. **모듈 규칙 "방 단위 키를 새로 만들면 `RoomLifecycleJob` 정리 목록에도 추가"의 의도된 예외다**(사용자 확정). 이유는 셋이다.
   - ① 두 키는 쓸 때마다 90초로 연장되는 짧은 TTL이라, 구독이 없어지면 90초 안에 스스로 사라진다. `chat:dedup:`·`chat:rate:`를 정리 목록에서 뺀 선례(game-chat.md 제약 9)와 같다.
   - ② 자정에 UNLINK하면 CHAT-GC-44로 아직 열려 있는 어제 방 스트림의 값이 흔들린다. 다음 생존 갱신(최대 15초)까지 0이나 1 적은 값이 나갔다가 원래 값으로 돌아온다(PR-22 위반).
   - ③ 두 키는 CHAT-GC-25(모든 `chat:*` 키에 TTL)를 TTL로 충족한다.
   
   `.claude/modules/chat.md`의 해당 규칙에 이 예외를 함께 적어야 한다(context-keeper).
2. **`SseEmitterRegistry.count(gameId)`는 파드 로컬 연결 수다.** 계정 고유 수도 아니고 방 전체 값도 아니다. 이 값을 `presence` 값이나 장애 폴백으로 쓰면 PR-1·2·23 위반이다.
3. **last-one-wins 축출의 순서는 "새 구독 등록 → 옛 구독 종료"다.** `SseEmitterRegistry.register`가 등록 뒤 `closeByUser`를 부르고, 원격 파드는 `chat-control` 명령으로 나중에 닫는다. 그래서 PR-9가 성립하려면 **새 구독의 소유자 기록(PR-5)이 옛 구독의 종료 판정보다 먼저 Redis에 반영돼 있어야 한다.** 같은 파드 재구독도 같은 순서다. 이 경우 소유자가 같은 파드라서 소유권만으로는 막을 수 없으므로, PR-8의 두 번째 조건("자기 파드에 그 방 구독이 더 없을 때")이 필요하다.
4. **소유자 확인과 삭제는 원자적이어야 한다**(PR-8). 확인과 삭제 사이에 다른 파드의 등록이 끼면, 방금 소유자가 된 등록을 지우게 된다. member와 소유 기록 중 하나만 지워진 상태도 생기면 안 된다.
5. **생존 시각은 Redis 서버 시각이다**(PR-30). `System.currentTimeMillis()` 같은 파드 시계로 score를 쓰거나 만료 경계를 계산하면, 파드 시계가 어긋난 만큼 일찍 빼거나 늦게 뺀다.
6. **하트비트 스케줄러 스레드는 방 수명 작업과 공유된다**(`SseEmitterRegistry.heartbeat` 주석). 생존 갱신이 주기를 하트비트와 공유하더라도, 그 Redis 왕복이 이 스레드를 붙잡으면 안 된다. 붙잡으면 Redis 타임아웃(2초) 동안 `:ping` 적재와 방 수명 작업이 함께 밀린다(PR-24).
7. **설정 키를 `ChatProperties`에 성분으로 넣으면 기존 테스트 여러 곳이 깨진다.** 이 테스트들이 정식 생성자를 직접 호출하기 때문이다(`.claude/modules/chat.md`, `ChatLikesProperties`를 따로 둔 이유). 좋아요와 같은 함정이다.
8. **`presence` 쓰기는 소켓 쓰기 규칙(CHAT-GC-89·90, 쓰기 풀 경유)을 따라야 한다**(PR-17). 집계 주기 스레드나 Redis 스레드가 소켓에 직접 쓰면, 느린 클라이언트 한 명이 그 방 전체 집계를 멈춘다.
9. 구현 뒤 갱신할 곳이 둘이다. `docs/api/game-chat.md`의 SSE 이벤트 표에 `presence` 행을 추가해야 한다(api-documenter). `.claude/modules/chat.md`의 Redis 키 목록에 두 키와 자정 정리 예외를 추가해야 한다(context-keeper).
