# 회원 간 차단 요구사항
> 상태: 승인됨 · 모듈: user (크로스 모듈: domain, quiz) · 최종 수정: 2026-09-30
> **미해결 질문 0건** — 2026-09-30 사용자 답변으로 전량 확정. 2026-09-30 사용자 승인.

## 배경 / 목적
회원이 특정 상대를 차단하면 그 상대와 서로 채팅(quiz 모듈)·랭킹(user 모듈)에서 보이지 않아야 한다는 요구다. 차단은 `user` 모듈이 쓰기 API를 갖지만, **차단 관계 자체(`domain`의 새 엔티티)를 quiz·user 두 모듈이 함께 읽어 각자의 노출 로직에 반영해야 하는 크로스 모듈 기능**이다 — 이 문서 하나가 세 모듈에 걸친 계약의 단일 출처다. `docs/requirements/user/support-selection.md`(응원 구단, 2026-07)·`docs/requirements/user/team-bq-ranking.md`(랭킹, 2026-09-04)와 마찬가지로 새 스키마를 도입하는 쓰기 경로이므로 같은 패턴(불변식·멱등성·검증 순서)을 따른다.

**이 문서가 처음 여는 구조적 질문**: 지금 이 저장소의 어떤 응답도 "다른 회원"을 가리키는 안정적 식별자(`id`·`uid`)를 노출하지 않는다 — 채팅 메시지(`MessageResponse`/`MessageEvent`)는 `senderNickname`만, 랭킹(`BqRankingResponse`)은 식별자를 **의도적으로** 아예 안 싣는다("계정 식별자(id·uid)·isMe 는 싣지 않는다" — 소스 주석). **2026-09-30 결정: 닉네임으로 식별한다** — 기존 두 응답(chat·ranking)을 전혀 건드리지 않는 쪽을 택했다. 대신 닉네임이 이 저장소에서 DB `UNIQUE` 제약이 아니라는 사실이 새로운 위험을 만든다 — 아래 "알려진 한계" 참고.

## 범위
- 포함: 차단 생성 API 1개, 차단 목록 조회 API 1개, `domain`의 신규 차단 엔티티 계약(컬럼·불변식 수준까지만 — 클래스/테이블명·FK `@OnDelete` 구체값은 `context-keeper`/`spring-dev` 판단), quiz 채팅 노출 차단의 동작 계약, user 랭킹 노출 차단의 동작 계약.
- 제외:
  - **차단 해제(unblock) API — 이번 스코프에서 명시적으로 제외한다.** 이번엔 차단(생성)·차단 목록 조회 두 API만 만든다. 해제는 후속 작업(2026-09-30 결정)이며, 해제 API가 추가되기 전까지 **차단은 영구적**이다(사용자가 스스로 풀 방법이 없다는 뜻 — 후속 작업 우선순위를 정할 때 참고).
  - **닉네임 DB `UNIQUE` 제약 추가 — 이번 스코프에 넣지 않는다.** 아래 "알려진 한계"의 위험을 안 채 진행하기로 한 결정이며, 필요해지면 별도 요구사항으로 논의한다(이 기능 하나 때문에 전역 닉네임 정책을 바꾸지 않음).
  - **채팅방 자체 접근 차단** — 차단은 방을 못 들어가게 막는 게 아니라 "그 상대가 보낸 메시지가 내 화면에서 안 보인다"는 뜻으로 확정했다(2026-09-30). 구단 단위 폐쇄방 가드(`CHATROOM_TEAM_MISMATCH` 등)는 이 기능과 무관하게 그대로다.
  - **차단 사유·메모** — 요청 원문에 없음.
  - **차단 대상에게 알림/통지** — 상대는 자신이 차단됐다는 사실을 API로 알 수 없다(조회해도 본인이 차단했는지만 알 수 있고, 차단당했는지는 이 문서 범위에서 노출하지 않는다).
  - **신고(report)와의 통합** — quiz 채팅의 기존 신고→blind 기능과 이 차단은 완전히 별개 트랙이다. 섞지 않는다.
  - **차단 대상의 다른 활동 제한**(퀴즈 좋아요·응원 등) — "채팅·랭킹에서 서로 안 보인다"는 원문 범위를 넘는 제한은 넣지 않는다.

## 알려진 한계
- **닉네임은 DB `UNIQUE` 제약이 아니다**(`.claude/modules/user.md` — 유일성은 `existsByNickname` 애플리케이션 검사로만 지켜지고, 예약 닉네임 사칭 방지도 문자 정책뿐이라고 명시돼 있다). 이론상 레이스로 동일 닉네임 계정이 둘 이상 존재할 수 있다. **그 경우 차단 요청이 어느 계정을 가리키는지는 모호하다** — 이 문서는 이 모호성을 해소하지 않고 **알고 있는 위험으로만 남긴다**(닉네임 `UNIQUE` 제약 추가는 범위 밖, 위 "범위" 참고). 구현 시 닉네임 조회가 복수 행을 만나는 경우의 동작(예: 그중 하나를 결정적으로 고르는지, 에러를 내는지)은 이 요구사항 문서가 규정하지 않는 미정의 동작이다.
- **차단은 이번 스코프에서 영구적이다** — 해제 API가 없으므로, 한번 차단하면 후속 작업이 나오기 전까지 사용자가 스스로 되돌릴 방법이 없다.

### 차단 해제 — **이번 스코프에서 제외 (후속 작업)**

이 구간의 ID는 예약하지 않는다 — 애초에 이번 개정 전까지 배정된 번호가 없었으므로 재사용 규칙과 무관하다. 해제 API가 후속 작업으로 진행될 때 새 번호(USER-BLK-13 이후)를 이어서 쓴다.

## 크로스 모듈 영향 요약 (이 기능이 손대야 하는 세 모듈)
- **domain**: 신규 차단 엔티티(위 USER-BLK-19~21) 1개 + 리포지토리. `user`가 이 테이블의 유일한 쓰기 주체이고(`ddl-auto=update`), `quiz`는 읽기 전용 소비자(`ddl-auto=none`)다 — `nickname_changed_at`/`profile_img_url` 선례와 같은 함정이 그대로 반복된다: **이 테이블을 quiz가 배포 전에 갖고 있지 않으면, 차단 필터링 코드가 `Unknown table`로 quiz 쪽 해당 경로 전체를 깨뜨린다.** 배포 순서는 domain 스키마(= user 앱의 `ddl-auto=update` 적용 또는 선행 마이그레이션 SQL) → quiz 배포 순으로 고정해야 한다(기존 컨벤션과 동일).
- **quiz**: `ChatService`의 메시지 조회 경로(`GET /rooms/{roomUid}/messages`)에 차단 필터 추가(USER-BLK-14~16). 전송·SSE 경로는 불변.
- **user**: 이 문서의 주 소유 모듈. 차단 생성·목록(USER-BLK-1~12) + `BqRankingService`의 목록·본인 순위 두 갈래에 차단 필터 추가(USER-BLK-17~18, `rankOf`/`countHigherInTeam`/`assignRanks` 전부 영향권).
