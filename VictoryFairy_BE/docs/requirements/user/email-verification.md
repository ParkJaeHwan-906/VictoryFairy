# 이메일 인증 요구사항
> 상태: **승인됨 (2026-09-18, 개정분)** · 모듈: user · 최종 수정: 2026-09-18
> 기존 USER-EMV-1~18은 2026-07-18 승인분이다. 이번 개정은 **USER-EMV-14 폐기 + USER-EMV-19~38 신설(23·24·25는 철회)**이며 2026-09-18 승인됐다.
> 2026-09-18 사용자 결정 반영 — 소셜 로그인은 범위 밖(메일 갈래 3→2), verify 열거 구멍은 더미 코드 저장으로 닫음.

## 배경 / 목적
회원가입 시 사용자가 입력한 이메일이 **실제 본인 소유인지** 확인할 방법이 없다. 지금 signup은 `@Email` 형식 검사와 `existsByEmail` 중복 검사만 하므로, 남의 이메일이나 존재하지 않는 이메일로도 가입이 가능하다. 이 기능은 **발송(인증번호를 이메일로 보냄) → 검증(이메일+인증번호 대조)** 2단계로 소유를 확인하는 두 API를 추가하고, **검증에 성공한 이메일만 가입**을 허용하도록 signup을 연동한다.

이 문서가 확정하는 것은 **두 인증 API의 동작 계약 + signup 연동 계약**이다.

## 2026-09-18 개정 — 계정 열거(account enumeration) 차단
`POST /api/auth/email/send-code`는 인증 없이 누구나 호출할 수 있는데, 이미 가입된 이메일이면 409(`DUPLICATE_EMAIL`), 소셜 전용 계정이면 409(`SOCIAL_ACCOUNT_ONLY` + provider 목록)를 돌려준다. 주소만 바꿔 가며 상태코드만 읽으면 **누가 이 서비스에 가입돼 있는지, 무엇으로 가입했는지**가 그대로 열람된다 — USER-EMV-14가 "중복가입 사전차단 우선"을 이유로 허용한 의도적 예외가, 지금은 서비스에서 가장 값싼 계정 열거기다.

개정의 핵심은 **정보를 없애는 것이 아니라 옮기는 것**이다: 응답은 두 갈래 모두 200으로 통일하고, 갈림은 **그 주소의 메일함 주인만 볼 수 있는 메일**에서 일어난다. 중복가입 사전차단 안내는 계속 전달되지만 수신자가 "요청을 보낸 사람"에서 "그 주소의 주인"으로 바뀐다.

**2026-09-18 사용자 결정 2건이 이 절의 전제를 바꿨다.**
- **소셜 로그인은 범위 밖이다** — 현재 연결돼 있지 않아 자체 로그인만 다룬다. 따라서 메일 갈래는 3개가 아니라 **2개**이고, 소셜 전용 안내 메일(구 갈래 3, USER-EMV-23~25)은 철회한다. `SocialOnlyAccountInspector`·`SOCIAL_ACCOUNT_ONLY`·`SocialAccountHintResponse`는 **건드리지 않는다** — 다만 send-code가 더 이상 그 예외를 던지지 않는다.
- **가입된 이메일에도 인증번호를 저장한다(메일로는 보내지 않는다)** — 저장하지 않으면 `verify`가 "코드 없음(`EXPIRED_VERIFICATION_CODE`)"과 "코드 틀림(`INVALID_VERIFICATION_CODE`)"으로 갈려, 요청 2회로 가입 여부가 그대로 드러난다. send-code만 200으로 통일하면 열거기가 한 단계 뒤로 옮겨질 뿐이다.

## 범위
- 포함:
  - 인증번호 **발송 API** — 이메일을 받아 인증번호를 생성·저장하고 해당 주소로 발송
  - 인증번호 **검증 API** — 이메일+인증번호를 받아 저장값과 대조하고 성공 시 "인증 완료" 상태를 저장
  - 인증번호 형식·유효시간(TTL)·재발송 쿨다운·시도 횟수 제한 정책
  - **signup 연동** — 인증 완료 상태가 아닌 이메일의 가입을 서버가 차단(기존 signup 계약 개정)
  - **(2026-09-18 개정)** send-code 응답을 사용 여부와 무관하게 200으로 통일하고, 갈림을 메일 본문 3갈래로 옮기는 계약(USER-EMV-19~31)
- 제외:
  - **로그인 응답시간 부채널** — 같은 목적(계정 열거 차단)의 별건이며 `docs/requirements/user/login-account-enumeration.md`(USER-LAE-*)가 담당한다.
  - **소셜 로그인 전반(`oauth.*`)** — 2026-09-18 사용자 결정: 현재 연결돼 있지 않아 자체 로그인만 다룬다. 소셜 전용 계정 안내 메일(구 갈래 3)·`oauth-login.md`(USER-OAU-46-1) 개정·`SOCIAL_ACCOUNT_ONLY` 정리는 전부 이번 범위 밖이다.
  - **소셜 링크/입력 티켓의 인증번호 경로(`OauthEmailVerificationService`)** — 그 경로의 발송은 **원래부터 계정 존재 여부로 갈리지 않는다**(쿨다운도 이메일이 아니라 티켓 단위). 이번 변경 대상이 아니며 한 줄도 바뀌지 않는다.
  - **signup의 `DUPLICATE_EMAIL` 409(그리고 `DUPLICATE_TEL`·`DUPLICATE_NICKNAME`)** — signup은 이메일 인증 통과가 선행조건이라 메일함을 못 여는 사람은 도달조차 못 한다. 열거 경로가 아니므로 그대로 둔다(USER-EMV-31).
  - **메일 본문의 문안·HTML 디자인** — 본문이 **무엇을 담아야 하는가**(인증번호 / 사용 중 안내 / provider 목록)까지가 이 문서의 계약이고, 정확한 문장은 구현 재량이다.
  - **로그인·비밀번호 재설정용 이메일 인증** — 목적이 회원가입 소유 검증으로 한정됨. 정책·저장소는 재사용 가능하게 두되 엔드포인트는 추가하지 않는다.
  - **실제 메일 템플릿(HTML/문구) 디자인** — 발송이 일어난다는 계약까지가 이 문서의 범위. 본문 문구는 구현 재량.
  - **인증 완료 상태를 signup 요청 본문의 토큰으로 전달하는 방식** — 서버가 Redis에 상태를 저장하고 signup이 이를 조회하는 방식으로 확정됐다(미해결 질문 6 답변 B). 단기 인증 토큰 발급(옵션 C)은 채택하지 않는다.

| 메일 제목 | **갈래별로 다름**(인증번호 메일은 현행 제목 유지) | 메일함은 주인만 보므로 제목이 갈려도 열거가 아님 |

**엔드포인트 (확정, 기존 `/api/auth/*` 컨벤션 따름):**
- 발송: `POST /api/auth/email/send-code`
- 검증: `POST /api/auth/email/verify`

### 수동 실측 항목 (자동 테스트로 강제하지 않는다)
- 갈래 1·2 각각 30회 send-code 후 서버 처리시간 중앙값을 비교한다. 기대: 차이가 SMTP 왕복 편차 범위 안이고, 한쪽만 체계적으로 빠르지 않다.
- 어긋나면 USER-EMV-30의 구조 동등성(코드 생성·저장·쿨다운·발송 각 1회)이 깨진 것이므로 그것부터 본다.

### 남는 열거 경로 (이 개정이 닫지 못하는 것)
- **비-prod 프로파일의 `LogEmailSender` 로그**는 갈래를 그대로 남긴다(클라이언트가 볼 수 없는 서버 로그라 열거 경로는 아니다).
- **소셜 전용 계정 여부**는 이 문서로 감춰지지 않는다 — 다만 send-code 응답에서는 갈래 2로 접혀 더 이상 드러나지 않고, 남는 것은 로그인 응답시간 쪽이다(`login-account-enumeration.md`의 "남는 한계", 소셜 로그인 연결 시 재검토).
- **응답시간**은 수동 실측까지가 계약이다(자동 강제 없음).

## signup 연동 (기존 signup 계약 개정)
이 기능으로 **기존 signup 요구사항이 개정된다.** 종전 signup은 형식 검증 + `existsBy*` 중복 검사만 통과하면 가입됐으나, 이제 **이메일 인증 완료(USER-EMV-15) 상태가 선행 조건**이 된다.
- 개정 전: `POST /api/auth/signup` → 형식·중복 통과 시 201.
- 개정 후: `POST /api/auth/signup` → **이메일이 Redis 인증 완료 상태일 때만** 형식·중복 검사로 진행. 미인증/만료면 USER-EMV-16/17로 거부(신규 `EMAIL_NOT_VERIFIED`). 가입 성공 시 인증 완료 상태 소비·제거(USER-EMV-18).
- 검사 순서(제약): 형식(Bean Validation, 400) → **이메일 인증 완료 여부(USER-EMV-16, `EMAIL_NOT_VERIFIED`)** → 중복(`existsBy*`, 409). 인증 완료 검사가 중복 검사보다 먼저인지 여부는 구현 재량이나, 세 단계가 모두 통과해야 가입된다. `SignupRequest` 본문 스키마는 그대로다(인증 상태는 서버 Redis 조회, 요청 필드 추가 없음).
- 이 개정은 `docs/api/auth.md`의 signup 명세에도 반영돼야 한다(`api-documenter` 소관).

## 구현 제약 (구현이 지켜야 할 사실 — 구현 방법 지시가 아님)
1. **Redis + spring-data-redis 도입이 전제다 — 현재 모듈 의존성에 없다.** `.claude/modules/user.md` 기준 현재 라이브러리는 Security/JPA/Validation/JJWT/BCrypt/MySQL/dotenv뿐이다. 인증번호·시도횟수·쿨다운·인증완료 상태를 전부 TTL 기반으로 보관할 **Redis**가 도입돼야 하고, `spring-data-redis` 의존성 추가와 `docker-compose`에 Redis 서비스 추가가 전제된다. 이는 확정 결정이 강제하는 **제약**이다(연결·직렬화 세부는 `spring-dev`).
2. **메일 발송은 SMTP + dev mock 전제.** 운영 프로파일은 `spring-boot-starter-mail`(SMTP) 실발송, 개발/테스트 프로파일은 실제 발송 없이 로그/mock으로 대체한다. dev에서 실메일을 보내지 않는 것이 확정 사항이다(발송 계약 검증은 mock 경계에서). SMTP 접속 정보는 환경변수로 주입(기존 `DB_*` 컨벤션과 동일 방식).
3. **새 ErrorCode가 필요하다(`:common`).** 현재 `ErrorCode` enum에는 이메일 인증용 코드가 없다(`DUPLICATE_*`, `UNAUTHENTICATED`, `INVALID_CREDENTIALS`, `INVALID/EXPIRED_REFRESH_TOKEN`뿐). 쿨다운(429, USER-EMV-5)·불일치(400, USER-EMV-10)·만료무효(400, USER-EMV-11)·시도초과(400, USER-EMV-12)·**이메일 미인증(USER-EMV-16/17, `EMAIL_NOT_VERIFIED`)** 전용 코드 추가가 전제된다. 중복 이메일 발송(USER-EMV-14, 409)은 기존 `DUPLICATE_EMAIL`을 재사용할 수 있다. ⚠ **2026-09-18 개정으로 이 경로의 409 자체가 사라진다**(USER-EMV-20) — `DUPLICATE_EMAIL`은 signup에서만 계속 쓰인다(USER-EMV-31). 429는 `status`가 int라 값 자체는 문제없으나 모듈에 **429 응답 선례가 아직 없다**(현재 400/401/409/204만).
4. **에러 응답 포맷은 기존 모듈 계약을 따른다.** Bean Validation 실패(USER-EMV-4/13)는 `{"success":false,"data":{"필드":"메시지"},"message":"입력값이 올바르지 않습니다."}`(400), `BusinessException`(USER-EMV-5/10/11/12/14/16/17)은 `{"success":false,"data":null,"message":"<ErrorCode 메시지>"}` + `ErrorCode.getStatus()`. `GlobalExceptionHandler`가 그대로 처리한다.
5. **DTO는 record.** 이 모듈의 요청/응답 DTO는 전부 record 컨벤션(`SignupRequest`, `LoginRequest`, `PasswordValidationRequest` 등). 새 발송/검증 요청 DTO도 동일하게.
6. **인증번호 대조는 형식 검증과 분리한다.** email/code의 `@NotBlank`/형식(400, Bean Validation)과 저장값 대조(BusinessException, USER-EMV-10/11)는 별개 단계다 — 형식 통과 후에만 대조를 수행한다.
7. **`/api/auth/**`는 이미 `permitAll`이라 `SecurityConfig` 수정 불필요**(USER-EMV-7). signup 연동도 같은 컨트롤러(`AuthController`)·같은 경로 prefix라 보안 규칙 변경 없음.

## 미해결 질문
미해결 없음 — USER-EMV-1~18은 2026-07-18에, 2026-09-18 개정분 질문 4건은 같은 날 사용자 결정으로 모두 해소됨.

### 2026-09-18 해소 기록
1. `verify`로 남는 열거 구멍 → **A(더미 코드 저장)**. 가입된 이메일에도 같은 키·TTL·시도 한도로 인증번호를 저장하되 메일에는 싣지 않는다. 종전 초안의 USER-EMV-22/25("생성·저장하지 않는다")를 뒤집어 USER-EMV-22/32~36으로 재작성.
2. 메일 발송 실패 시 응답 → **A(현행대로 전파)**. 갈래와 무관하게 동일하게 실패하므로 열거 경로가 아니고, 사용자에게 성공으로 오인시키지 않는다(USER-EMV-38).
3. 탈퇴 계정 점유 이메일 → **A(갈래 2 "이미 사용 중")**. 종전 `DUPLICATE_EMAIL`과 같은 자리.
4. 메일 제목 → **갈래별로 다르게**. 인증번호 메일 제목은 현행 유지(USER-EMV-37).
5. (추가 결정) **소셜 로그인은 범위 밖** — 메일 갈래가 3개에서 2개로 줄고 USER-EMV-23/24/25가 철회됐다.

## 기존 정책과의 충돌
### 2026-09-18 개정분
- **`SOCIAL_ACCOUNT_ONLY`의 유일한 사용처가 사라진다 — 다만 이번엔 아무것도 지우지 않는다.** send-code가 더 이상 그 예외를 던지지 않으므로 `SOCIAL_ACCOUNT_ONLY`·`SocialAccountHintResponse`·`SocialOnlyAccountInspector`는 호출되지 않는 채로 남는다. **삭제를 요구하지 않는다**(소셜 로그인이 범위 밖이라 그 정리도 범위 밖이다 — 2026-09-18 결정).
- **`oauth-login.md`의 USER-OAU-46-1이 이 개정과 어긋나게 된다.** 그 요구사항은 "소셜 전용 활성 계정 이메일이면 send-code가 409 `SOCIAL_ACCOUNT_ONLY` + `data.providers`"를 계약으로 두고 있는데, USER-EMV-19/20이 그 409를 없앤다. **그 문서의 개정은 이번 범위 밖이며, 어긋난다는 사실만 여기 기록한다.**
- **`EmailSender` 포트의 메서드가 `sendVerificationCode(email, code)` 하나뿐이다.** 갈래 2는 인증번호가 실리지 않는 메일이라 이 시그니처로 표현할 수 없다 — **두 갈래(인증번호 발송 / 이미 사용 중 안내)를 표현할 수 있어야 한다**는 것이 계약이 강제하는 제약이다(구현 방법 지시가 아님). `SmtpEmailSender`(prod)·`LogEmailSender`(비-prod) 두 구현 모두 해당하며, 비-prod 구현이 갈래를 구분해 남겨야 테스트가 갈래를 확인할 수 있다.
- **"가입된 주소에는 통과시킬 코드가 없어야 한다"는 직관과 정면으로 어긋난다(USER-EMV-22).** 가입된 이메일에도 인증번호를 저장하는 것은 의도된 선택이며, 안전은 두 겹으로 담보된다: ①그 값은 메일로 나가지 않아 사용자가 알 수 없고(USER-EMV-32) ②설령 맞혀 인증 완료 상태를 만들어도 signup이 409 `DUPLICATE_EMAIL`로 막는다(USER-EMV-31/36). **USER-EMV-32가 깨지면 이 구조가 통째로 무너진다** — 안내 메일 본문에 코드를 실수로 싣는 순간 남의 가입 이메일로 인증이 통과된다.
- **`docs/api/auth.md`의 send-code 절 전체가 사실과 어긋나게 된다**(409 2종·`SOCIAL_ACCOUNT_ONLY` 분기 설명·실패 예시 JSON). 구현 후 `api-documenter` 소관.
- **`.claude/modules/user.md`의 "send-code 409는 의도적 예외" 항목**과 엔드포인트 표의 `POST /api/auth/email/send-code ... (가입된 이메일 409)`가 뒤집힌다. Redis 키 규약 항목(`code:{email}`이 미가입 이메일에만 생긴다는 전제)도 함께 갱신 대상이다. `context-keeper` 소관.
- **`OauthEmailVerificationService`와의 정합은 오히려 좋아진다.** 그 클래스는 처음부터 "발송 응답이 계정 존재 여부로 갈리지 않는다"를 계약으로 두고 있었고(javadoc), 이번 개정으로 자체 가입 경로가 **같은 원칙으로 수렴**한다. 그 경로 자체는 변경 대상이 아니다.
- **`login-account-enumeration.md`(USER-LAE-*)와 짝이다.** 같은 목적의 앞뒷면이라 **함께 적용되어야 의미가 있다**.

### 2026-07-18 승인분 (기록 유지)
- **계정 존재 비노출 철학과의 의도적 예외(USER-EMV-14).** ⚠ **2026-09-18 개정으로 이 예외는 철회된다**(아래는 당시 판단의 기록이다). 모듈은 login(`INVALID_CREDENTIALS`로 미가입/탈퇴/오답 통합)·validate에서 계정·가입 이력을 노출하지 않는다. send-code에서 이미 가입된 이메일에 409 `DUPLICATE_EMAIL`을 주면 **가입 이력이 노출**돼 이 원칙과 어긋난다. **사용자가 계정 비노출보다 중복가입 사전차단을 우선하기로 명시적으로 결정**했으므로, 이 지점은 비노출 원칙의 **의도적 예외**로 기록한다(signup은 종전대로 이 예외를 따르지 않고 `existsBy*` 중복 시 409를 이미 반환하므로, send-code 409는 signup의 기존 노출 수준과 정합).
- **stateless 아키텍처와 Redis.** 모듈은 `SecurityConfig`가 stateless + JWT다. 인증번호·인증완료 상태를 HTTP 세션이 아니라 **Redis에 애플리케이션 상태로** 보관하므로 stateless 요청 처리와 상충하지 않는다(세션 저장소를 도입하지 않음).
- 그 외 signup의 이메일 형식 제약(`@NotBlank @Email @Size(max=100)`)·에러 응답 포맷과는 정합(USER-EMV-4/13이 그대로 재사용). signup 흐름 자체는 USER-EMV-16~18로 개정되며, 이는 "signup 연동" 절에 명시.
