# 사용자 정의 퀴즈방 요구사항
> 상태: 승인됨 (2026-10-14, 개정 1차) · 모듈: quiz(엔드포인트·서비스·SSE·주간 확정 잡) + domain(신규 엔티티·리포지토리) · 최종 수정: 2026-10-14
> ID 계열 `QUIZ-CQR-<n>`. 절마다 번호 블록을 띄워 뒀다(1~, 10~, 30~ …). 빈 번호는 예비 번호다. **번호는 재사용하지 않는다.**
> **개정 1차 (2026-10-14, 승인됨)**: 사용자가 정책 하나를 더했다. 원문은 "인기 퀴즈방은 일주일 단위로 갱신됩니다. 그리고 일주일 이후 변경되는 시점에는, 주간 베스트 top 5 퀴즈방의 소유자에게 bq가 아닌 포인트 500 포인트를 지급합니다."이다. 이 때문에 **결정 8(인기 정렬 공식)이 개정됐다**. 요청마다 `likeCount + solvingCount`로 계산하던 방식이 주 단위 확정으로 바뀐다. **QUIZ-CQR-33은 폐기**하고(번호 보존) K절 QUIZ-CQR-130~148로 대체한다. QUIZ-CQR-34·63·76에 개정 메모를 달았다. 새로 생긴 결정 15~26과 QUIZ-CQR-144는 같은 날 사용자가 전부 A안으로 확정했다(결정 기록). 결정 1~7·9~14는 그대로다.
> **정정 (2026-10-14)**: QUIZ-CQR-83의 인수 기준 예시만 고쳤다. 기존 예시는 "같은 계정이 두 파드에 동시에 구독한 상태가 유지된다"를 전제했는데, 이는 QUIZ-CQR-92(퀴즈방끼리 last-one-wins, 파드 간 축출)와 모순이다. 그래서 축출 전 과도 구간을 예로 바꿨다. 요구사항 문장과 의미는 그대로다(prod 2인스턴스 컨테이너 검증에서 발견).

## 배경 / 목적
지금 퀴즈는 AI 파이프라인이 만든 문제를 경기 중에 이닝 단위로 받는 것뿐이다. 이 기능은 사용자가 직접 만든 문제 묶음(퀴즈방)을 커뮤니티 공간에 올리고, 다른 사용자가 경기와 상관없이 그것을 풀게 한다. 같은 방을 지금 풀고 있는 사람 수와 보기별 선택 분포는 SSE로 밀어 준다. 폴링 GET은 두지 않는다.

**기존 오늘의 퀴즈 경로와 섞이지 않게 하는 것이 이 문서의 숨은 축이다.** 이유는 두 가지다. ① 미편성 풀(`quizzes.quiz_date IS NULL`)은 매일 편성 잡이 `/today` 세트로 끌어간다. ② quiz 앱의 SSE 레지스트리는 같은 계정의 구독을 방에 상관없이 축출한다. H절과 QUIZ-CQR-91이 이 두 가지를 제약으로 적는다.

## 범위
- 포함:
  - 퀴즈방 생성. 방 제목, 방 소개, 문항 1~20개를 받는다. 문항은 객관식(보기 2~4개) 또는 O/X다
  - 퀴즈방 전체 목록(페이징)·인기 top 5·상세 조회. 인기 top 5는 **주 단위로 확정한 주간 베스트**다(개정 1차, K절)
  - **주간 베스트 확정과 보상.** 주가 바뀌는 시점에 주간 베스트 top 5 방의 소유자에게 point 500을 지급한다. bq는 주지 않는다(개정 1차, K절)
  - 퀴즈 리스트 불러오기. 정답은 싣지 않는다
  - 문항별 답 제출(확정 2026-10-14, 결정 1). 마지막 문항에 답하면 결과(맞은 개수/총 문항, 문항별 내 답·정답)를 바로 반환한다
  - 퀴즈방 추천(설정·해제)
  - 퀴즈방 SSE: 풀이 중 인원(`presence`)과 문항별 보기 선택 분포(`votes`)
  - 기존 오늘의 퀴즈 경로와의 격리 제약
  - 탈퇴 계정 데이터 처리
- 제외:
  - **퀴즈방 수정·삭제**(확정 2026-10-14, 결정 9). 수정은 이미 끝난 풀이 결과를 소급해서 바꾼다(`Quiz.content` 수정 문제와 같은 성격, `.claude/modules/domain.md`)
  - **결과 재조회 API**(확정 2026-10-14, 결정 3). 결과는 마지막 문항 제출 응답에만 실린다
  - **재풀이**(확정 2026-10-14, 결정 3). 계정당 방 하나에 한 번만 풀 수 있다
  - **풀이에 대한 point·bq 적립**(확정 2026-10-14, 결정 4). 주간 베스트 보상(K절)은 풀이 적립이 아니라 방 소유자에게 주는 별도 지급이다
  - **주간 베스트 보상 알림**, 지난 주차 베스트·지급 이력 조회 API, 응답의 순위·주차 필드(확정 2026-10-14, 결정 25·26)
  - **해설 필드**(확정 2026-10-14, 결정 11)
  - **욕설 마스킹·거절**(확정 2026-10-14, 결정 10). 커뮤니티 게시글과 같은 결정이다(`community.md` 범위 제외)
  - 퀴즈방 신고·블라인드, 관리자 기능, 검색, 작성 횟수 제한
  - 차단 관계(`user_blocks`)에 따른 목록 필터링
  - 퀴즈방 목록·상세 REST로 투표 분포를 주는 것. 분포는 SSE로만 나간다(QUIZ-CQR-95)
  - 풀이 시간 제한. 문항별 시한(기존 퀴즈의 8분)은 두지 않는다
  - 접속자 명단(닉네임 목록). 인원 숫자만 낸다
  - 커뮤니티 게시판 API(`/api/community/**`)의 응답 변경(확정 2026-10-14, 결정 12)

## 용어
| 용어 | 정의 |
|---|---|
| **퀴즈방** | 작성자 한 명, 제목, 소개, 문항 1~20개로 이루어진 묶음 |
| **문항** | 퀴즈방 안의 문제 하나. 유형은 `객관식` 또는 `O/X`이고, 보기와 정답 보기 번호 하나를 가진다 |
| **보기 번호(`no`)** | 문항 안 보기의 0부터 시작하는 순번. 기존 `quiz_options.option`과 같은 축이다. O/X는 0=O, 1=X |
| **풀이** | 한 계정이 한 퀴즈방에서 문항에 답해 가는 과정. 모든 문항에 답하면 **완료**다 |
| **풀이 중 인원** | (확정 2026-10-14, 결정 5) 그 퀴즈방 SSE를 지금 구독하고 있는 **고유 계정 수**. 모든 파드를 합친 값이다. 같은 계정의 연결이 여러 개여도 1로 센다 |
| **투표 분포** | 문항 하나의 보기별 선택 계정 수. 완료 여부와 상관없이 지금까지 커밋된 모든 답을 센다 |

## 엔드포인트 (확정 2026-10-14 — 경로·이름은 구현에서 바뀔 수 있다. 바뀌면 이 표와 인수 기준을 함께 고친다)
전부 quiz 앱(`/rt`)에 있고 인증이 필요하다.

| 메서드 | 경로 | 요청 | 성공 응답 |
|---|---|---|---|
| POST | `/rt/quiz-rooms` | `{title, description, quizzes:[{type, question, options[], answer}]}` | 201 `{roomId}` |
| GET | `/rt/quiz-rooms` | `?page=&size=` | 200 `PageResponse<RoomSummary>` |
| GET | `/rt/quiz-rooms/popular` | 없음 | 200 `List<RoomSummary>`(가장 최근에 확정된 주간 베스트, 최대 5 — 개정 1차) |
| GET | `/rt/quiz-rooms/{roomId}` | 없음 | 200 `RoomDetail` |
| GET | `/rt/quiz-rooms/{roomId}/quizzes` | 없음 | 200 `List<RoomQuiz>` |
| POST | `/rt/quiz-rooms/{roomId}/quizzes/{quizId}/answer` | `{option}` | 200 `{answeredCount, total, result}` |
| PUT | `/rt/quiz-rooms/{roomId}/like` | `{liked: true\|false}` | 200 `{liked, likeCount}` |
| GET | `/rt/quiz-rooms/{roomId}/subscribe` | 없음 | 200 `text/event-stream` |
| DELETE | `/rt/quiz-rooms/{roomId}/subscribe` | 없음 | 200 |

응답 형태:
- `RoomSummary`: `{roomId, title, description, author{nickname, profileImgUrl}, quizCount, likeCount, solvingCount, createdAt}`
- `RoomDetail`: `RoomSummary`의 키 + `{liked, isAuthor}`
- `RoomQuiz`: `{quizId, type, question, options[{no, text}]}`. `answer` 키는 없다
- `result`: `{correctCount, total, quizzes[{quizId, type, question, options[{no, text}], myOption, answer, correct}]}`
- SSE `presence`: `{"count": n}` / SSE `votes`: `{"quizId": q, "options": [{"no": 0, "count": c}, …]}`

## 결정 기록 (2026-10-14, 사용자 확정)
1. **답을 문항마다 내는가, 다 풀고 한 번에 내는가.** → **확정(2026-10-14): A안** 이 답에 따라 "실시간 투표율"의 뜻이 바뀐다.
   - A(확정): 문항별 제출. 다른 사람이 풀고 있는 동안에도 분포가 실시간으로 움직인다. 서버가 미완료 풀이를 저장해야 하고 엔드포인트가 1개 늘어난다(E절).
   - B: 일괄 제출(`POST …/submit {answers:[…]}`). API가 단순하고 미완료 상태를 서버가 몰라도 된다. 대신 분포는 "다 푼 사람들의 선택"이고 제출 순간에 문항 수만큼 한꺼번에 움직인다. QUIZ-CQR-50~55가 1건으로 합쳐진다.
2. **문항별 정오를 언제 알려 주는가** → **확정(2026-10-14): A안**(결정 1이 A안일 때만 해당).

## 기존 정책과의 충돌 / 제약 (모듈 컨텍스트 대조 결과)
1. **미편성 풀 흡수.** `QuizPublishService`는 `quizzes`에서 `quiz_date IS NULL AND team_id IS NULL`인 문항을 공통 쿼터로 `/today` 세트에 스탬프한다. 퀴즈방 문항이 이 조건에 맞는 모양으로 같은 테이블에 들어가면 남이 만든 문제가 오늘의 퀴즈로 나간다. 그때 point·bq도 적립된다. 바닥 단계(team·player·game 전부 null)로도 선택된다 → QUIZ-CQR-100~102.
2. **SSE 축출 범위.** quiz 앱 `SseEmitterRegistry.register()`는 같은 계정의 구독을 **방에 상관없이 전부** 끊는다(last-one-wins). 퀴즈방 구독이 같은 레지스트리를 쓰면 퀴즈방에 들어가는 순간 그 계정의 구단 채팅(`/rt/chat`) 스트림이 끊긴다 → QUIZ-CQR-91.
3. **파드 로컬 인원.** quiz `realtime`의 레지스트리 구독 수는 파드별 값이다. 구단 채팅 참여 인원은 이 이유로 노출을 롤백했다. 퀴즈방 인원과 인기 정렬은 파드 간 집계가 없으면 부정확하다 → 결정 6, QUIZ-CQR-37·83.
4. **quiz `SecurityConfig`에는 ASYNC 디스패치 permitAll이 없다**(알려진 미수정 문제). 서버가 퀴즈방 스트림을 `complete()`하면(축출·퇴장·타임아웃) ERROR 로그가 남을 수 있다. 새 SSE 경로도 같은 영향을 받는다.
5. **스키마 배포 순서.** quiz는 prod `ddl-auto=none`이다. 신규 테이블은 user 앱이 먼저 떠서 만들거나 선행 SQL로 만들어야 하고, 안 그러면 퀴즈방 경로 전체가 500이다. 작성자 FK를 CASCADE 없이 두면(QUIZ-CQR-121) `expired-data-cleanup.md`의 이관 단계를 먼저 개정해야 한다. 안 그러면 첫 하드 삭제 회차가 FK 위반으로 실패한다(커뮤니티 USER-CM-205와 같은 구조).
6. **선례끼리의 갈림.** 추천 API 형태(커뮤니티 PUT 상태 지정 vs 퀴즈 좋아요 POST 토글), 추천 자격(커뮤니티 제한 없음 vs 퀴즈 좋아요 "푼 문제만"), 욕설 처리(커뮤니티 미적용 vs 채팅 마스킹)가 기존 승인 문서마다 다르다. 본 문서는 앞쪽으로 확정했다 → 결정 10·14, QUIZ-CQR-77.
7. **(개정 1차) 지금 구현과 어긋난다.** 같은 worktree의 미커밋 구현은 인기 top 5를 매 요청마다 계산한다(`QuizRoomService.getPopularRooms`, `QuizRoomRepository.findTop5ByOrderByLikeCountDescIdDesc` + Redis 실시간 인원). 이건 폐기된 QUIZ-CQR-33의 동작이다. QUIZ-CQR-130·131을 만족하도록 다시 만들어야 한다.
8. **(개정 1차) 주 경계와 저장 시각의 시간대.** `QuizRoomLike.createdAt`·`QuizRoomAnswer.createdAt`은 `@CreationTimestamp`라 JVM 기본 시간대(파드는 UTC)로 찍힌다. KST 월요일 0시 경계를 그 값과 그대로 비교하면 9시간 어긋난다(커뮤니티 엔티티가 `Clock`(KST) 주입으로 바꾼 이유, `QuizSubmitWindow`가 `kstClock`을 쓰지 않는 이유와 같은 함정) → QUIZ-CQR-133. 스케줄 cron도 `zone = "Asia/Seoul"`을 명시해야 한다. 빠뜨리면 09:00 KST에 돈다(`QuizIngestScheduler`·chat `RoomLifecycleScheduler` 선례).
9. **(개정 1차) 추천 취소는 행을 삭제한다.** 그래서 "그 주의 추천"은 확정 시점까지 남은 행으로만 셀 수 있다. 같은 주에 추천→취소→재추천하면 1개로 센다(QUIZ-CQR-134의 "취소되지 않은").
10. **(개정 1차) 다중 파드 중복 지급.** quiz의 기존 잡은 분산 락이 없다. `QuizIngestScheduler`는 `uk_quizzes_external_id` UNIQUE가 중복을 막는 심판이고, 편성은 과편성을 "무해"로 허용했다. 하지만 point 지급은 중복되면 무해하지 않다. user의 `CleanupExecutionLock`(Redis SET NX 락)은 자기 javadoc에서 TTL·분단 시 겹칠 수 있다고 인정한다. 그러니 QUIZ-CQR-143은 락만으로는 보장되지 않고, DB 단에서 (주, 방) 중복을 거절하는 심판이 필요하다는 제약이다(어디에 둘지는 구현 판단).
11. **(개정 1차) point 적립 경로의 락 규칙.** `UserAccount.addPoint`는 `UserAccountRepository.findWithLockById`로 계정 행을 잠근 뒤에만 호출해야 한다. 오늘의 퀴즈 제출과 상점 구매가 같은 행을 잠그므로 QUIZ-CQR-145는 이 규칙을 지키면 성립한다. 보상은 bq를 건드리지 않으니 `users_bq` 락은 필요 없고, 락 순서(계정 → `users_bq`)와 충돌할 경로도 없다.
12. **(개정 1차) 스키마와 정리 배치.** 확정 결과·지급 기록을 새 테이블로 두면 quiz `ddl-auto=none`이라 `infra/sql/migrate-quiz-room.sql`에 함께 넣어야 한다. 그 테이블이 `users_account`를 참조하면 `AccountFkDeleteRuleInspector`·만료 데이터 정리의 FK 규칙 목록에도 들어가야 한다(제약 5와 같은 구조).
