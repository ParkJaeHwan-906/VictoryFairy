# domain 모듈

> domain 작업 시에만 로드되는 슬림 컨텍스트. (공통: `com.skhynix` 독립 앱, `:common`=ApiResponse/BusinessException/ErrorCode, MySQL+spring-dotenv, prod `ddl-auto`는 앱마다 다름 — user=`update`, quiz=`none`)

## 책임
프로젝트 전체 JPA 엔티티·리포지토리를 담는 `java-library` 모듈. 자체 실행 앱이 아니라 **포트 없음**. `user`·`quiz` 두 모듈이 이 모듈을 참조해 엔티티를 공유한다.

## 패키지 구성 (`domain/src/main/java/com/skhynix/domain/`)
각 도메인 패키지는 `entity`/`repository` 하위 패키지로 나뉜다(예: `com.skhynix.domain.user.entity.User`, `com.skhynix.domain.user.repository.UserRepository`) — 전 도메인 공통 구조.
- `user` — `User`, `UserAccount`, `UserRefreshToken`, `UserBq`, `Gender`(enum) + 각 리포지토리(`UserBq`는 계정 종속 위성 엔티티라 별도 패키지를 파지 않고 여기 둔다 — 형제 없이 혼자라 `record`/`chat`/`support`처럼 패키지를 얻을 이유가 없고, 같은 성격의 `UserRefreshToken`이 이미 여기 있다)
- `team` — `Team` + `TeamRepository`
- `player` — `Player` + `PlayerRepository`
- `stadium` — `Stadium` + `StadiumRepository`
- `game` — `Game`, `GameStatus`(코드 테이블), `GameLineup`, `Position`(코드 테이블), `InningHalf`(enum, 진행 중 경기의 이닝 초/말) + `GameRepository`, `GameStatusRepository`, `GameLineupRepository`, `PositionRepository`
- `record` — `BatterRecord`, `PitcherRecord` + 각 리포지토리 (경기×선수 1행 집계형 야구 기록 도메인, `game_id`/`player_id` FK로 `Game`/`Player` 참조. 원천은 네이버 record API 박스스코어이며 py-collector 가 멱등 upsert — 구 이벤트형 설계의 `BatResult`/`PitchResult` 결과코드 테이블은 폐기됨)
- `chat` — `Chatroom`, `Chat` + `ChatroomRepository`, `ChatRepository` (`Chat`은 `Chatroom` 종속 하위 개념이라 별도 최상위 도메인 대신 `chat` 패키지로 통합 — `record` 패키지가 연관 엔티티를 묶은 선례와 동일 논리)
- `support` — `UserSupportTeam`, `UserSupportPlayer` + 각 리포지토리 (사용자가 구단/선수를 응원한다는 사실. `record`/`chat` 패키지가 연관 엔티티를 묶은 선례와 동일 논리로 한 패키지에 통합)
- `quiz` — `QuizType`(코드 테이블), `Quiz`, `QuizOption`, `QuizUserSubmit` + 각 리포지토리 (문제·보기·제출 기록. `record`/`chat`/`support`와 동일 논리로 한 패키지에 통합. ⚠ 이 패키지는 **`quiz` 모듈(앱)과 이름만 같고 별개다** — 그 모듈이 지금 서빙하는 건 채팅뿐이다)

## 엔티티 → 테이블 (클래스 단수, 테이블 복수형 — 단수 테이블 4건은 예외)
`User`→`users` · `UserAccount`→`users_account` · `UserRefreshToken`→`users_refreshtoken` · `UserBq`→`users_bq`(사용자 확정 — `UserAccount`/`UserRefreshToken`과 같은 `users_`+한정어 형태라 아래 단수 4건과 달리 규칙 위반이 아니다) · `Team`→`teams` · `Player`→`players` · `Stadium`→`stadiums` · `Game`→`games` · `GameStatus`→`game_statuses` · `GameLineup`→`game_lineups` · `Position`→`positions` · `BatterRecord`→`batter_records` · `PitcherRecord`→`pitcher_records` · `Chatroom`→`chatrooms` · `Chat`→`chats` · `UserSupportTeam`→`user_support_team` · `UserSupportPlayer`→`user_support_player` · `Quiz`→`quizzes` · `QuizOption`→`quiz_options` · `QuizType`→`quiz_type` · `QuizUserSubmit`→`quiz_users_submit`(끝이 단수). 새 엔티티에 임의로 단수 테이블명을 쓰지 말 것 — 뒤 4건(`user_support_team`·`user_support_player`·`quiz_type`·`quiz_users_submit`)은 **사용자가 이름을 직접 준 것**이 유일한 근거인 명시적 예외다. 사용자 DDL 초안을 받았을 때의 기준이 여기서 나온다: **이름은 초안을 따르고**(의미가 안 드러날 때만 고친다 — 초안의 `quiz_users_submit.Field`→`is_answer`), **`nullable` 같은 제약은 domain 컨벤션으로 덮는다**(초안이 `NOT NULL`이던 `quizzes.team_id`/`player_id`를 nullable로 바꾼 게 그 사례 — 아래 "퀴즈 출제 대상" 참고).

## FK 관계 (전부 단방향, 역방향 `@OneToMany` 없음)
- `UserAccount` → `User` (`@OneToOne` LAZY, optional=false, unique 조인 컬럼) + `@OnDelete(CASCADE)`
- `UserBq` → `UserAccount` (`@OneToOne` LAZY, optional=false, unique 조인 컬럼) + `@OnDelete(CASCADE)` — **새 1:1 관계는 `@ManyToOne` + `@Table(uniqueConstraints)`를 쓰지 않는다.** Hibernate가 owning `@OneToOne` 조인 컬럼에 unique를 자체 부여하므로 `@Table(uniqueConstraints)`를 겹치면 같은 컬럼에 unique 인덱스가 2개 생길 위험이 있다(`UserAccount`→`User`가 선례, 새 1:1 엔티티 추가 시 다시 밟기 쉬운 함정)
- `UserRefreshToken` → `UserAccount` (`@ManyToOne` LAZY, optional=false) + `@OnDelete(CASCADE)`
- `Player` → `Team` (`@ManyToOne` LAZY, optional=false) + `@OnDelete(CASCADE)`
- `Game` → `Team`(home/away, 둘 다 optional=false) / `Stadium`(optional=true, nullable) / `GameStatus`(optional=false) — **`@OnDelete` 없음**
- `GameLineup` → `Game`/`Team`/`Player`(`@ManyToOne` LAZY, optional=false 셋 다) + `@OnDelete(CASCADE)` / `Position`(`@ManyToOne` LAZY, optional=true, `position_id` nullable) — **`@OnDelete` 없음**(마스터 데이터 취급, `positions` 행이 지워져도 `game_lineups`는 보존)
- `BatterRecord`/`PitcherRecord` → `Player`, `Game` (`@ManyToOne` LAZY, optional=false 둘 다) + `@OnDelete(CASCADE)`
- `Chatroom` → `Team` (`@ManyToOne` LAZY, optional=false) + `@OnDelete(CASCADE)`
- `Chatroom` → `UserAccount`(owner, `@ManyToOne` LAZY, optional=false) — **`@OnDelete` 없음**
- `Chat` → `Chatroom`/`UserAccount` (`@ManyToOne` LAZY, optional=false 전부) + `@OnDelete(CASCADE)`
- `UserSupportTeam` → `UserAccount`/`Team` (`@ManyToOne` LAZY, optional=false 둘 다) + `@OnDelete(CASCADE)`
- `UserSupportPlayer` → `UserAccount`/`Player` (`@ManyToOne` LAZY, optional=false 둘 다) + `@OnDelete(CASCADE)`
- `Quiz` → `QuizType`(`@ManyToOne` LAZY, optional=false) / `Team`·`Team`(**opponentTeam** — 맞대결 상대)·`Player`·`Game`(`@ManyToOne` LAZY, **optional=true, 넷 다 nullable**) — **전부 `@OnDelete` 없음**. `QuizType`은 코드 테이블(`Game → GameStatus`와 같은 정책), `Team`/`Player`는 **문제의 실체가 아니라 분류 태그**라서다 — 문제는 사람이 쓴 콘텐츠라 수집기로 재생성되지 않는데, CASCADE면 `DELETE FROM players` 한 줄이 문제→보기→**전 사용자 제출 기록**까지 조용히 지운다(제출 기록은 중복 제출 차단의 유일한 근거라, 지워지면 이미 푼 문제를 다시 풀고 점수를 다시 받는다). non-cascade면 대신 `ERROR 1451`로 시끄럽게 실패한다(실측) — 앱·수집기 어디에도 선수·구단 삭제 경로가 없어 이 제약이 막는 건 수동 DB 작업뿐이고, **복구 불가능한 소실 vs 되돌릴 수 있는 에러**의 비대칭이 근거다.
- `QuizOption` → `Quiz` (`@ManyToOne` LAZY, optional=false) + `@OnDelete(CASCADE)`
- `QuizUserSubmit` → `UserAccount`/`Quiz`/`QuizOption`(제출한 보기) (`@ManyToOne` LAZY, optional=false 셋 다) + `@OnDelete(CASCADE)`

**CASCADE 정책 기준**: 팀·구장·경기상태·포지션 같은 **마스터 데이터**는 삭제돼도 그걸 참조하는 경기·라인업·기록이 연쇄 삭제되면 안 되므로 `@OnDelete` 없음(`Game → Team`/`Stadium`/`GameStatus`, `GameLineup → Position`이 이 경우). 반면 참조 엔티티에 완전히 종속되어 "삭제 시 함께 사라져도 되는" 데이터는 CASCADE — `GameLineup → Game`/`Team`/`Player`(라인업은 해당 경기·선수 없이 존재할 수 없음), `BatterRecord`/`PitcherRecord`(원본 `Player`/`Game`이 사라지면 집계 기록도 같이 사라져야 함), `Chatroom → Team`(채팅방은 팀 종속 데이터, 사용자 결정)·`Chat → Chatroom`/`UserAccount`, `UserSupportTeam`/`UserSupportPlayer` → `UserAccount`/`Team`/`Player`(응원 기록은 계정·대상에 완전히 종속돼 계정이나 대상이 사라지면 함께 사라져도 됨), `UserBq → UserAccount`(누적 점수는 계정에 완전히 종속)가 이 경우다. 즉 마스터데이터라고 무조건 non-cascade인 게 아니라 **"삭제되면 함께 사라져도 되는 종속 데이터인가"**가 기준이다. 새 FK 추가 시 이 기준으로 판단할 것. 같은 `Chatroom` 엔티티 안에서도 FK마다 정책이 다를 수 있다: `owner`(소유자 `UserAccount`)는 방이 소유자 계정 삭제와 무관하게 보존돼야 하는 공용 자원이고, 계정 삭제가 소프트삭제(`exit_at`)라 고아 FK가 애초에 생기지 않으므로 `Game → Team`과 같은 non-cascade다.

## 엔티티 작성 컨벤션 (새 엔티티 추가 시 따를 것)
- `@Entity` + `@Table(name = 복수형_스네이크)`, `@Getter`, `@NoArgsConstructor(access = PROTECTED)`. `@Setter` 두지 않음.
- PK: `@GeneratedValue(IDENTITY)` + `@Column(name = "id")` — **내부 전용**, API·URL에 노출하지 않는다
- 외부 노출이 필요하면 `id`와 별개로 `uid` 컬럼을 둔다(현재 `UserAccount`, `Chatroom` 두 곳에서 사용): `VARCHAR(36)` + UUID v4(`UUID.randomUUID().toString()`)를 **애플리케이션에서** 생성, private 생성자 본문에서 채우고 `@Builder` 파라미터로는 받지 않는다(타임스탬프와 같은 계열의 컨벤션). 목적은 순차 PK 열거 방지(예: SSE 구독 URL). Hibernate `@UuidGenerator`는 쓰지 않음. `Chat`은 uid 없음 — 개별 메시지는 외부 식별자 노출 요건이 없다.
- 모든 컬럼에 `length`/`nullable` 명시, 기본은 `nullable = false`
- 생성은 `private` 생성자 + `@Builder`. **타임스탬프는 생성자 파라미터로 받지 않는다** (Hibernate가 자동 채움)
- 타임스탬프 정책: **마스터/기준 데이터**(`User`, `UserAccount`, `Team`, `Player`, `Stadium`, `GameStatus`, `Position`)와 **갱신되는 엔티티**(`Game` — 진행 중 점수·상태가 바뀜, `Chatroom` — 참여인원/이름/소프트삭제로 갱신, `Chat` — blind/소프트삭제로 갱신, `GameLineup`/`BatterRecord`/`PitcherRecord` — py-collector 가 멱등 upsert로 적재해 백필 재실행·사후 확정(decision 등)으로 값이 갱신될 수 있음)는 `@CreationTimestamp created_at`(updatable=false) + `@UpdateTimestamp updated_at` 둘 다. **기록성 엔티티**(`UserRefreshToken` — 한 번 쌓이면 수정 안 함)는 `created_at`만. ⚠ `QuizUserSubmit`(제출 기록)은 기록성인데도 `updated_at`이 있다 — 재제출을 새 행이 아니라 **같은 행 갱신**으로 처리할 여지를 열어둔 것이지 실수가 아니다(아래 중복 제출 항목 참고).
- `Game`에는 **`winner` 컬럼이 없다** — 승자는 별도 컬럼으로 저장하지 않고 `home_score`/`away_score` + `game_status`에서 파생시키는 설계다(정규화, 스코어와 승자 불일치 방지).
- Enum은 `@Enumerated(ORDINAL)` + `columnDefinition = "TINYINT"`, **선언 순서 변경 금지** (예: `Gender` MALE=0/FEMALE=1)
- 상태 전이가 필요하면 `@Setter` 대신 **엔티티가 자신의 전이를 책임지는 의도 노출 메서드**를 둔다(예: `UserAccount.withdraw(LocalDateTime)`/`isWithdrawn()` — 이미 전이된 상태면 no-op으로 최초 값을 보존; 같은 패턴으로 `Chatroom.join()`/`leave()`(0 하한)/`delete(LocalDateTime)`/`isDeleted()`, `Chat.blind()`/`unblind()`/`delete(LocalDateTime)`/`isDeleted()`)
- 인덱스가 필요하면 `@Table(indexes = {@Index(...)})`로 명시한다 — domain 최초 사례는 `Chat`의 `idx_chats_chatroom_created(chatroom_id, created_at)`(히스토리 페이징: chatroom_id 등치 필터 + created_at DESC 정렬을 인덱스만으로 만족). 두 번째가 `Quiz`의 `idx_quizzes_quiz_date`(오늘의 퀴즈 조회 축). `QuizUserSubmit`의 `idx_quiz_users_submit_account_quiz`는 **`uk_quiz_users_submit_account_quiz` UNIQUE 로 승격돼 사라졌다**(2026-08-07 — 같은 컬럼 쌍에 인덱스가 둘이 되지 않게 별도 추가가 아니라 승격). prod 인덱스 생성은 `user`의 `ddl-auto=update`에 의존한다(Flyway 없음) — 위 "prod 스키마는 user 앱이 만든다" 참고.
  ⚠ **"인덱스가 없다"는 판단을 FK 컬럼에 대해 내리지 말 것** — InnoDB는 FK마다 단일 컬럼 인덱스를 자동 생성한다. 그래서 질문은 항상 "FK 자동 인덱스로 충분한가"이고, 복합 조건일 때만 답이 아니오다. 위 퀴즈 인덱스가 그 경우로, 없으면 `WHERE user_account_id=? AND quiz_id=?`가 index_merge intersect로 풀리고 스캔 길이가 **"그 문제를 푼 사람 수"에 비례해 자란다**(실측 20만 행: intersect 100+1235행 0.16ms → 인덱스 단건 0.006ms, `existsBy`는 커버링으로 테이블 접근 0회). 반대로 `QuizOptionRepository.findAllByQuiz_IdOrderByOptionAsc`는 `Using filesort`가 붙어도 정렬 대상이 한 문제의 보기 2~5행뿐이라 **인덱스를 더하지 않는 게 맞다** — 실행계획에 filesort가 보인다고 반사적으로 추가하지 말 것.
- UNIQUE 제약이 필요하면 `@Table(uniqueConstraints = {@UniqueConstraint(...)})`로 명시한다 — domain 최초 사례는 `UserSupportTeam`의 `uk_user_support_team_account_team(user_account_id, team_id)`와 `UserSupportPlayer`의 `uk_user_support_player_account_player(user_account_id, player_id)`, 그리고 코드 테이블 쪽 `GameStatus.uk_game_statuses_name`·`QuizType.uk_quiz_type_name`, **적재 멱등키 `Quiz.uk_quizzes_external_id`**(S3 후보 `quizId` — 파드 동시 실행·재시도의 중복 차단을 DB가 심판. `games.naver_game_id`와 같은 "외부 생산자 식별자 보관" 계열), **중복 제출 차단 `QuizUserSubmit.uk_quiz_users_submit_account_quiz`**(1회 제출 확정에 따른 승격). **제약 이름을 반드시 명시한다** — `@Column(unique=true)`의 Hibernate 자동 생성명(`UK6x04…`)을 쓰면 나중에 손으로 도는 1회성 DDL과 이름이 달라 "이미 걸렸는지"를 확인할 수 없다.
- CHECK 제약이 필요하면 `@Table(check = {@CheckConstraint(...)})`로 명시한다(JPA 3.2 표준 애너테이션 — `org.hibernate.annotations.@Check`는 Hibernate 7에서 deprecated라 쓰지 않는다. 동일 DDL 생성 확인됨) — domain 최초 사례는 `Game`의 `ck_games_current_inning`(`current_inning BETWEEN 1 AND 11`)·`ck_games_inning_half`(`inning_half IN (0, 1)`). UNIQUE·인덱스와 같은 이유로 **제약 이름을 반드시 명시**한다. ⚠ 다만 **`ddl-auto=update`가 기존 테이블에 CHECK를 거는지는 UNIQUE처럼 단정할 수 없다** — 아래 `ddl-auto=update` 항목의 실측 참고. ⚠ `@Enumerated(ORDINAL)` 컬럼은 Hibernate가 서수 범위 체크를 **자동으로** 붙일 수 있다 — `add column`에 딸려 `games_chk_N`(자동 생성명, 환경마다 다름) 형태로 나간다(2026-08-11 devdb·로컬 실측. prod에는 안 나갔다). 선언한 CHECK를 1회성 DDL로 나중에 추가할 때 이 자동 생성 제약이 있으면 먼저 DROP해야 같은 뜻의 CHECK가 두 개 남지 않는다 — **있는지 없는지는 `information_schema.CHECK_CONSTRAINTS`로 환경마다 조회해 확인할 것.**
- **이미 행이 있는 테이블에 NOT NULL 컬럼을 추가**할 때는 `@ColumnDefault("...")` + 자바 필드 초기값을 함께 둔다 — domain 최초 사례는 `UserAccount.point`/`UserBq.bqScore`(둘 다 `@ColumnDefault("0")` + `= 0L`). 전자는 `ddl-auto=update`가 만드는 `ALTER TABLE ... DEFAULT 0`으로 **기존 행**을 채우고, 후자는 애플리케이션이 만드는 **신규 행**을 채운다 — 하나만 있으면 한쪽 경로에서 0 보장이 깨진다. `columnDefinition`을 쓰지 않는 이유는 `nullable = false`가 만드는 `not null`과 문구가 중복되고 위 `columnDefinition`이 `length`를 덮어쓰는 함정을 피하기 위해서다. `@Builder` 파라미터로는 받지 않는다(`uid`/`exitAt`과 같은 계열 — 항상 정해진 초기값에서 시작해야 함).

- **`quiz_options.option`은 MySQL 예약어라 `@Column(name = "`option`")`처럼 백틱이 필요하다**(실측: 백틱 없이 `CREATE TABLE t (option TINYINT)`는 ERROR 1064). 백틱을 지우면 `ddl-auto=update`가 만드는 DDL이 문법 오류로 실패해 **user 앱이 기동하지 못한다.** 이 값은 화면 표기용 보기 번호이며(O/X는 **0=O, 1=X** — S3 후보 계약의 A=O→0, B=X→1 순번. 종전 "0=X, 1=O" 서술은 계약과 반대라 정정) `Quiz.answer`와 같은 축이라 **둘 다 `TINYINT`로 폭을 맞췄다**(같은 축인데 폭이 다르면 스키마만 보고는 같은 축임이 안 드러난다). `answer`를 `QuizOption` FK로 바꾸면 `quizzes → quiz_options → quizzes` **순환 참조**가 생겨 2단계 쓰기가 강제되고 컬럼이 nullable이어야 하므로 지금 설계가 맞다 — 대가는 참조 무결성 부재다(`answer=3`인데 보기가 1,2뿐인 "풀 수 없는 문제"를 스키마가 막지 않으니 **출제 저장 시 검증 필수**). `answer`는 보기 행을 가리키는 FK가 아니라 **번호 값**이라 보기를 재생성해도 정답이 깨지지 않는다. 대신 **같은 문제 안에서 보기 번호가 겹치는 것도 스키마가 막지 않는다** — 보기 세트를 통째로 갈아끼우는 편집과 충돌할 수 있어 `(quiz_id, option)` UNIQUE를 미부여했고, 이것도 쓰기 경로 몫이다.
- ⚠ **`QuizUserSubmit.submitOption`의 CASCADE는 보기를 지우면 제출 기록을 함께 지운다** — 실측: 제출 2000행이 달린 문제의 보기만 지웠더니 **제출이 0행**이 됐다. `Quiz.answer`를 FK가 아닌 번호 값으로 둔 게 정확히 이 취약함을 피하려는 설계인데 이 FK만 그걸 되살리는 **설계 내부 모순**이다. **그럼에도 현행 유지가 사용자 결정이다** — 보기를 편집·삭제하는 경로가 아직 없어 지금은 발생할 수 없고, 안 쓸 대비책은 복잡도만 남기기 때문. **재검토 시점은 「보기 편집 기능을 만들 때」로 고정**하고, 그때 ① 번호 값 전환(제출 기록 자립, 대신 고른 텍스트 복원 불가) ② `SET_NULL` + nullable(최소 변경, 제출·`isAnswer` 보존을 실측 확인) 중에 고른다. **`RESTRICT`는 쓸 수 없다** — InnoDB가 `quizzes` 삭제를 `quiz_options` 쪽으로 먼저 연쇄시켜 **문제 통째 삭제까지 ERROR 1451로 실패**한다(실측). 그때까지의 임시 방편은 보기 수정을 DELETE+INSERT 가 아니라 **UPDATE 로만** 하는 것(행 id 유지 → FK 안 깨짐)이나, 스키마가 강제하지 않는 규율이고 `@OneToMany(orphanRemoval)`에 새 리스트를 넣는 흔한 구현이 내부적으로 DELETE+INSERT라 의식하지 않으면 밟는다. 보기 개수 축소는 UPDATE 로 해결되지도 않는다.
  같은 성격의 문제가 **`Quiz.content`(문제 지문)에도 있다** — 지문을 고치면 과거 제출이 "이 사람은 (지금 지문)에 이렇게 답했다"로 소급해 읽힌다. 완전 차단은 문제 자체의 버전 관리가 필요한데 MVP 범위 밖이라 열어둔다(채점 결과 자체는 `isAnswer` 스냅샷이라 어느 경우에도 안전하다).
- **`QuizUserSubmit.isAnswer`는 제출 시점에 확정해 저장한다** — `submitOption.option`과 `quiz.answer` 비교로 매번 재계산할 수도 있지만, 정답이 나중에 정정되면 과거 채점 결과까지 소급해 뒤집혀 이미 지급한 점수와 어긋난다. **한 사용자의 같은 문제 중복 제출은 `uk_quiz_users_submit_account_quiz` UNIQUE 가 막는다**(2026-08-07 승격 — 1회 제출 확정. 제출 기록이 점수 적립 근거라 동시 요청 race 차단은 DB 몫). 위 "`ddl-auto=update`는 기존 테이블에 UNIQUE를 추가하지 않는다"에 걸리므로 테이블이 이미 있던 환경은 **`infra/sql/migrate-quiz-ingest.sql` 1회 적용 필수**(dev·prod 둘 다 — dev 2026-08-07·prod 2026-08-08 실측 모두 구모양 테이블 존재. 위 quiz_type 항목 참고). `Quiz.score`는 "MVP 이후"에서 **적재 시 채우는 배점으로 전환**됐다(S3 후보 `pointReward` — 난이도 연동, scoring.yaml 정본). 사람이 쓴 퀴즈는 여전히 null 가능.
- **상태값 ↔ 네이버 API 매핑** (원천: py-collector `docs/data-formats.md` "경기 상태 판정"): `SCHEDULED`=`statusCode "BEFORE"` / `IN_PROGRESS`=`"LIVE"` / `FINISHED`=`"RESULT"` / `DRAW`=`"RESULT"`+양팀 동점 / `CANCELED`=`cancel == true`. **취소 경기는 `statusCode`가 `"RESULT"`가 아니라 `"BEFORE"`로 오고 점수가 0-0 껍데기**이므로 CANCELED 는 반드시 `cancel` 플래그로 판정할 것. 네이버가 내려주는 `suspended`(서스펜디드 — 중단 후 재개)는 아직 목록에 없다. 코드 테이블이라 필요해지면 행만 추가하면 되고 배포는 필요 없다.
