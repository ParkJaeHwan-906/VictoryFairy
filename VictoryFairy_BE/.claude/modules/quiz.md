# quiz 모듈

> quiz 작업 시에만 로드되는 슬림 컨텍스트. (공통: `com.skhynix` 독립 앱, `:common`=ApiResponse/BusinessException/ErrorCode, `:domain`=엔티티/리포지토리, MySQL+spring-dotenv, prod `ddl-auto`는 앱마다 다름 — user=`update`, quiz=`none`)

## 책임
Quiz 도메인 REST API 서버. **구단별 채팅 기능 구현 완료**: `chat`(방 목록/상세·구독·퇴장·전송·히스토리·신고 REST+SSE) + `realtime`(SSE 실시간 전달) + `chat/profanity`(전송 경로 욕설 마스킹). **채팅방은 응원 구단 단위 폐쇄 공간**(목록·방 단위 경로 전부 구단 가드) **+ 서버 주도 구독 종료**(명시적 퇴장, 중복 구독 last-one-wins 축출). **퀴즈 기능**: `quiz`(S3 quiz-candidates → RDB 적재 + 매일 편성(전원 동일 데일리 세트) + 조회·개별 조회·제출(채점/**point·bq 두 축 적립**)·풀이 이력·좋아요 토글 API). **포트 8081.**

## 핵심 클래스 (`quiz/src/main/java/com/skhynix/quiz/`)
- `QuizApplication` — 메인 진입점. `scanBasePackages = "com.skhynix.quiz"`로 **좁게** 스캔 (user는 `com.skhynix` 전체). `@EntityScan`/`@EnableJpaRepositories`만 `com.skhynix` 전역.
- `SecurityConfig` — stateless, `@Import({JwtVerificationConfig.class, GlobalExceptionHandler.class})`로 `web-support`의 JWT 검증 부품 + 예외 어드바이스를 명시적으로 끌어옴(좁은 스캔이 `com.skhynix.websupport.*`를 놓쳐 자동 감지 안 됨). `securityFilterChain`이 `JwtAuthenticationFilter`를 직접 `new`로 생성하며 `UserAccountRepository`(`:domain`, uid→id 조회)도 함께 넘김 — `web-support`의 필터 생성자가 바뀌면 여기도 같이 고쳐야 함. `/`, `/error`, `GET /health` 외 전부 인증 필수. 미인증 401도 `web-support`의 `RestAuthenticationEntryPoint`를 그대로 import해 등록(동일 커플링 — 생성자 바뀌면 같이 고칠 것)
- `chat/controller/ChatController` — `/rt/chat/**` REST+SSE. principal은 `@AuthenticationPrincipal Long userAccountId`(`JwtAuthenticationFilter`가 주입). `DELETE /rooms/{roomUid}/subscribe`(명시적 퇴장)도 이 인증 규칙에 자연히 걸림(SecurityConfig 수정 불필요)
- `chat/service/ChatService` — 방 조회/구독/퇴장/전송/히스토리/신고 로직. **채팅방은 응원 구단 단위 폐쇄 공간**: 목록·방 단위 경로 전부 요청자의 현재 응원 구단(`user_support_team.oppose is null`)과 방의 구단이 같아야 하고, 판정 순서는 **404(방 존재) → 400(`SUPPORT_TEAM_REQUIRED`, 응원 구단 없음) → 403(`CHATROOM_TEAM_MISMATCH`, 구단 불일치)로 고정**이다. `unsubscribe()`(퇴장)만 예외 — **가드를 걸지 않고 전면 멱등**이다(구단 일치도, 응원 구단 존재도, 방 존재·비삭제도 검사 안 함 — 정리 요청을 막으면 구단을 바꾼 사용자가 낡은 연결을 못 닫는다). 전송 성공 후 SSE 발행은 fire-and-forget(예외 삼킴, 저장·응답은 되돌리지 않음). 구독 성립·퇴장 시 종료 명령도 같은 커밋-후-발행 경로를 탄다. **2026-09-03 전송 경로만 응원 구단 조회가 `findWithTeamByUserAccount_IdAndOpposeIsNull`(`@EntityGraph` 판, `:domain`에 이미 있던 메서드)로 바뀌었다** — 치환어 결정에 `teams.code`가 필요한데 LAZY 프록시에서 읽으면 고빈도 전송 경로에 SELECT가 하나 더 붙기 때문이다(판정·순서 404→400→403은 그대로고 **SELECT 수도 종전과 같다**). 다른 채팅 경로(목록·구독·히스토리·신고)는 여전히 `findByUserAccount_IdAndOpposeIsNull`을 쓴다
- `chat/profanity/*`(신설 2026-09-03, 계약 `docs/requirements/quiz/chat-profanity-filter.md` 승인됨) — **채팅 욕설 마스킹**. `ProfanityFilter.mask(content, teamCode)`를 `ChatService.sendMessage`가 **`Chat` 엔티티 생성 직전에** 부른다(엔티티 안에서 부르면 domain이 필터 데이터에 의존하게 되고 탈퇴자 메시지 이관 등 필터를 안 쓰는 경로까지 영향권에 든다). 저장·201 응답·SSE **세 곳이 같은 마스킹 문자열**이고 **원문은 어디에도 저장하지 않으며 마스킹 여부 플래그도 없다**(DDL 0건·신규 `ErrorCode` 0건). **금지어가 있어도 거절하지 않는다(201)** — 실패 시 원문 저장 fallback도 없다. 치환어는 `MaskWordTable`이 발신자 구단 `teams.code`별 후보에서 **매칭된 원문의 `hashCode`로 결정적으로** 고른다(무작위·시각·계정 id 미개입 → 파드·재기동 무관 동일, code가 null이거나 표에 없으면 공통 폴백). ⚠ **구단별 후보 목록의 순서가 계약의 일부다** — 해시로 고르므로 단어를 **추가만 해도** 기존 치환 결과가 이동해 값을 고정한 테스트가 깨진다(목록 변경 = 테스트 갱신 동반). 판정 장치(`TextNormalizer`·`TracedText`·`KeyboardMapper`·`ProfanityPatterns`)와 리소스 `quiz/src/main/resources/profanity/`의 JSON 4종(`banned_words`·`exceptions`·`normalization`·`whitespace_strict`)은 **`VictoryFairy_AI/validation/`의 파이썬 구현을 이식한 것**이고 런타임에 그 앱을 호출하지 않는다(고빈도 경로를 다른 앱 가용성에 묶지 않음) — **두 쪽 목록·장치는 수동 동기화 대상**이라 갈리면 같은 문장이 채팅에서는 걸리고 AI 검증에서는 통과한다. `ProfanityDataLoader`+`ProfanityFilter` 생성자는 **기동 시 JSON 4종을 읽고 패턴을 컴파일하는 fail-fast**다 — 리소스가 누락되거나 형식(예: `single_char` 키 한 글자 제약)을 어기면 빈 생성이 실패해 **앱이 기동 자체를 못 한다**(필터가 조용히 꺼진 채 도는 것이 이 기능이 막으려는 결과라 의도된 선택 — 배포 시 알고 있어야 할 성질)
- `realtime/RealtimeEventPublisher` — 실시간 전송 포트(토픽=roomUid). **quiz 정답 집계 등 향후 기능도 재사용할 일반 설계**. 구현은 프로파일로 갈린다: `prod`=`RedisPubSubPublisher`(단일 채널 `realtime:events` 로 발행) + `RealtimeEventSubscriber`/`RealtimeRedisConfig`(리스너 컨테이너가 전 파드에서 수신 → 자기 레지스트리로 전달), `!prod`=`InMemoryPublisher`. 발행 파드도 자기 구독으로 되받으므로 Redis 구현은 로컬 레지스트리로 직접 전달하지 않는다(이중 전달 방지 — 테스트로 고정). quiz-app HPA maxReplicas=4 이므로 이 경로가 없으면 스케일아웃 시 메시지가 조용히 유실된다. **버스에는 전송 이벤트 외에 제어 신호 `subscription-close`(`SubscriptionCloseCommand`)도 실린다** — 양쪽 수신 측(`InMemoryPublisher.publish`/`RealtimeEventSubscriber.onMessage`) 모두 `SubscriptionCloseCommand.isCloseSignal(event)`로 전송(`registry.publish`)과 종료(`registry.handleCloseCommand`)를 분기한다. 분기를 빠뜨리면 종료 명령이 구독자에게 `data:`로 새어 나간다. `originInstanceId`(발행한 `SseEmitterRegistry.instanceId()`)로 발행 파드가 되받은 자기 명령을 무시한다 — 없으면 방금 연 새 구독이 자기 축출 명령에 끊긴다
- **이 앱은 시드를 넣지 않는다.** `spring.sql.init` 배선도, `build.gradle` 의 `processResources` 복사도 없다(실측: `quiz/build/resources/main/` 에 `sql/` 디렉터리 자체가 없음). 기본 데이터(구단 10개·SYSTEM 계정·구단별 채팅방 10개·경기 상태 5행·퀴즈 유형 2행)는 전부 **`user` 앱이 dev·prod 기동 시** `infra/sql` 의 시드 4종으로 채운다 — 테이블을 만드는 앱과 채우는 앱을 하나로 모은 결과다(`.claude/modules/domain.md` 참고).
  ⚠ **빈 DB 에 `:quiz:bootRun` 만 하면 스키마는 서지만 데이터가 비어 있다.** `@EntityScan("com.skhynix")` + dev `ddl-auto=update` 라 domain 엔티티 전체(2026-08-07 기준 22테이블)가 생기지만 시드는 0행이라, 채팅방 목록이 비거나 첫 출제가 `quiz_type` FK 위반으로 실패한다. 설정을 의심하기 전에 **`:user:bootRun` 을 한 번 띄울 것.** (테이블 수는 domain 엔티티가 늘 때마다 바뀌니 판정 근거로 쓰지 말 것.)
- `realtime/SseEmitterRegistry` — 방별 SSE 구독 관리(발신자 제외 fan-out), 죽은 연결을 하트비트로 회수. 타임아웃 30분·하트비트 15초(`:ping` 주석 프레임). `register()`는 `rooms.compute(...)`로, `remove()`는 `rooms.computeIfPresent(...)`로 구현되어 있다 — Set에 넣고 빼는 일과 빈 Set을 맵에서 걷어내는 일을 같은 빈(bin) 잠금 아래 원자적으로 묶기 위함. **`computeIfAbsent`+람다 바깥 `add`로 "단순화"하면 고아 Set 레이스가 재발한다**: 마지막 퇴장(Set 비어 맵에서 제거)과 신규 입장(같은 Set을 얻어 add)이 겹치면 새 구독이 맵에서 떨어져 나간 Set에 갇혀 fan-out·하트비트 순회에서 누락된다(해당 사용자는 메시지를 못 받음). `count(roomUid)`는 남아 있으나 프로덕션 호출부는 없음(테스트·진단용 접근자). **참여 인원(participants)은 어디에도 서빙되지 않는다** — 인메모리 구독 수는 파드별 값이라 다중 파드에서 부정확하고, DB 컬럼 집계는 connect/disconnect마다 write가 폭주해 RDB 집계+Redis 재계산까지 구현했다가 방향 전환으로 전부 롤백했다(제품 결정). `Chatroom.participants`/`join()`/`leave()`는 되살릴 여지를 남기려는 의도적 결정으로 domain에 남아 있으나 quiz는 미사용
  - **서버 주도 종료가 신설됐다**: `closeSubscriptions(roomUid, userAccountId)`(그 방만, 명시적 퇴장) · `closeAllSubscriptions(userAccountId)`(방 무관 전부, 축출의 원격 처리분) · `handleCloseCommand(roomUid, command)`(버스로 받은 종료 명령 처리 — `command.originInstanceId()`가 자기 `instanceId()`와 같으면 무시). `instanceId()`(인스턴스 식별용 랜덤 UUID)를 종료 명령에 실어 발행 파드가 되받은 자기 명령을 무시하게 한다
  - `register()`가 **last-one-wins 축출**을 한다 — 같은 사용자의 기존 구독을 방 불문 전부 끊고 새 구독만 남긴다(**멀티탭이 사실상 금지된다**: 같은 계정 두 탭이면 먼저 연 탭이 끊긴다). **`emitter.complete()`는 반드시 `compute`/`computeIfPresent` 람다 밖에서 불러야 한다** — `complete()`가 태우는 `onCompletion` 콜백이 `remove()`로 같은 맵을 재귀 갱신해 `ConcurrentHashMap`의 재귀 갱신 금지 계약을 깬다. 축출 구현(등록과 기존 연결 제거를 한 흐름에 묶는 지점)이 위 고아 Set 레이스 픽스를 가장 깨뜨리기 쉬운 자리다 — `compute` 바깥에서 remove 후 add 하는 형태로 풀면 그 회귀 테스트(AC-CHAT-11-5·55-2)가 다시 깨진다
- `realtime/RealtimeSchedulingConfig` — `@EnableScheduling`으로 하트비트 구동(quiz 좁은 스캔 범위 안이라 자동 등록). **`quiz/ingest`의 `@Scheduled`(일일 적재)도 이 활성화에 얹혀 돈다**
- `quiz/ingest/*` — **S3 → RDB 퀴즈 적재**. `QuizCandidate`(스펙 4.3 계약 record — evidence·settlement 등 저장 안 하는 필드는 일부러 안 받음, Jackson 3 기본이 모르는 필드 무시), `QuizCandidateReader`(`quiz-candidates/{date}/` 읽기 전용, 파일 단위 실패 격리), `QuizIngestService`(후보당 1트랜잭션 — KNOWLEDGE만 적재·PREDICTION 스킵, format→quiz_type 이름 매핑(OX→`O/X`, BINARY/MULTI4→`객관식`), answer A→0 번호 변환, subject→FK 해석. **정답 유출 방지 규칙**: subject는 문제가 '전제'하는 엔티티만 담겨 오므로 로더가 `player.getTeam()` 등으로 보강하면 안 됨. 예외: game 해석 성공 시 홈=team·원정=opponentTeam 채움. 해석 실패는 해당 FK만 null. **배점도 축이 둘**(`point`=후보 `pointReward` 그대로, `bq`=후보 `bqReward` 우선·없으면 `DifficultyBqMapping`(package-private, quiz 모듈 유일 정의)이 `difficulty`로 계산(EASY=1·MEDIUM=2·HARD=3·EXPERT=4, 5는 예약값이라 미부여) — `bqReward`는 v3 계약부터 필수가 됐지만 S3에 이미 쌓인 v3 이전 파티션에는 없어 이 폴백이 실제로 도는 경로다. 매핑표 없는·null 난이도는 `bq` null(적립 0, 적재 실패시키지 않음)), `QuizIngestScheduler`(cron 10:30 KST + 최근 3일 catch-up — 루틴이 08:50+60분 상한이라 30분 여유. **분산 락 없음(의도)**: `uk_quizzes_external_id` UNIQUE가 파드 동시 실행의 심판이고 위반은 "이미 적재됨"으로 삼킴. **적재 후 오늘만 `publishDaily` 호출** — 과거 날짜 편성 금지, 지난 세트는 동결), `QuizIngestStartupRunner`(기동 시 1회 — 10:30 이후 재시작한 파드의 사각 메움, 실패해도 기동 계속)
  - **`quiz_date` = 출제일(생성일 아님), NULL = 미편성 풀.** 적재 시 게임 귀속 후보(naverGameId 명시 — game FK 해석 실패여도)만 파티션 날짜를 스탬프하고, 나머지(역대기록형 등 시효성 없음)는 NULL 풀에 쌓는다. 스테일한 "오늘 경기" 문구가 풀에서 나중에 튀어나오는 것을 막는 규칙
- `quiz/service/QuizPublishService` — **매일 편성**: 그날 세트가 `quiz.serve.daily-count`(기본 10)에 못 미치면 풀에서 부족분만 `UPDATE ... NX`로 연장 금지 — **Redis 7.0+ 전제**(NX 옵션이 6.x엔 없어 명령이 에러 나고 그 에러가 아래 예외 삼킴에 먹혀 TTL 없는 영구 키로 남는다). **Redis 실패(초기화·읽기 모두)는 어댑터가 WARN 로그로 요청당 1건만 삼킨다** — 실패해도 `/today`는 200이고 전 보기 0이라, **`voteCount:0`은 "아무도 안 골랐다"와 "못 읽었다"를 한 모양으로 덮어 응답만으로 구별 불가**하다(알고 수용한 제약, 구별은 WARN 로그로만). 호출부 두 곳 다 try/catch하지 않으므로, `QuizVoteTally`의 다른 구현체를 추가한다면 그 구현도 예외를 삼켜야 한다는 게 암묵 계약이다(대가로 그 표는 영구 유실, 정본(`quiz_users_submit`)과 어긋난 채 남고 재구성 배치는 없다). **프로파일 분기가 없다** — 같은 앱의 실시간 fan-out(`RedisPubSubPublisher`)은 여전히 `@Profile("prod")`지만, 이 어댑터는 dev·prod 둘 다 실제 Redis에 쓴다("일관성" 명목으로 `@Profile("prod")`를 붙이지 말 것 — 2026-08-19 docker 실측으로 dev·prod 양쪽 기동 정상 확인)
- `quiz/dto/OptionResponse(no, text)`(공통 — 상세·결산 전용, 종전 `QuizResponse.OptionResponse`를 최상위로 옮김) ↔ `quiz/dto/QuizResponse.TodayOptionResponse(no, text, voteCount)`(`/today` 전용) — **의도적으로 갈라 둔 타입**이다. 상세·제출·이력 3경로는 불변인데, 이 둘을 다시 하나로 합치면 `voteCount`가 그쪽으로 새어 나간다 — 특히 `GET /{quizId}`는 미제출 상태에서도 호출 가능해 문제 id 순회로 분포를 긁을 수 있게 된다(컴파일·테스트 통과로 조용히 깨지는 회귀라 3경로에 `voteCount` 키 부재 단언이 회귀 고정으로 들어가 있다)
- `global/config/QuizIngestConfig` — `S3Client`(자격증명 코드에 없음: 로컬 `~/.aws`, prod IRSA — **prod 배포 전 quiz 파드 ServiceAccount에 crawl 버킷 `quiz-candidates/*` 읽기 IRSA 필요(dev_infra 소관)**) + `kstClock` 빈

## 엔드포인트 — 퀴즈 (`/rt/quizzes`) — 전부 인증 필수
- `GET /today?gameId=&preferredOnly=` → **`gameId` 필수**(값은 내부 PK 가 아니라 `games.naver_game_id` 문자열 — `GameResponse.gameId`로 이미 노출된 그 값). 지목된 경기가 존재·오늘(KST)·요청자의 응원 구단 참여·`IN_PROGRESS` 4종을 통과하고 그 이닝에 아직 안 받았어야 세트를 준다 — 하나라도 아니면 403 `QUIZ_NOT_SERVABLE`, 그 이닝에 이미 받았으면 409 `QUIZ_ALREADY_SERVED_IN_INNING`. 통과하면 오늘(KST) 세트 중 **행이 없는(=아직 안 받은) 문제만**(재조회 없음 — 아래 "재조회 폐지" 참고) **선호 먼저·그 안에서 사용자별 고정 랜덤**(전 사용자 동일 순서 아님 — 앞쪽 문제로 제출 쏠림 방지). `{id, type(객관식|O/X), question, difficulty, point, bq, preferred, options[{no,text,voteCount}]}` — **정답 미포함**. `bq`는 `point`와 같은 규칙(null도 키를 남김, `@JsonInclude` 없음). `voteCount`는 서빙 시점 Redis 스냅샷(장애·미보정도 0 — 위 `QuizVoteTally` 참고). **이 목록은 정의상 전부 미제출인데도 voteCount가 실린다** — "투표율은 제출을 마친 문제에만 노출"이던 종전 계약은 폐기됐다(사용자 결정, `docs/requirements/quiz/quiz-vote-exposure.md` 승인됨 2026-08-19). 대가는 다수결 정답 유출 + "늦게 받을수록 정보가 많다"는 불균형 — **2026-09-03부터 `bq_score`가 실제로 적립되므로 이 불균형은 더 이상 무해하지 않다**(종전 "현재 bq_score 미연동이라 점수엔 미반영"은 폐기, 재검토 대상이지만 이번 변경 범위 밖). 빈 배열 = **줄 수 있는데 줄 게 없다**(오늘 세트 없음 · 남은 문제를 이미 다 받음)는 뜻이고, "지금은 줄 수 없다"는 전부 에러(403/409)다 — 이 두 경로는 Redis를 안 건드린다. **응답 개수 상한 20**(`quiz.serve.max-today-count`)이고, 실린 문제마다 `quiz_users_submit`에 미답 행이 생기는 것 자체가 제출 자격이다(**Redis 제출 티켓은 폐기됨**) — 상한에 잘려 나간 문제는 행이 안 생겨 제출도 403이다. **좋아요 필드는 안 실린다** — 이 목록의 항목은 정의상 전부 미제출이라 전원 좋아요 불가, `QuizLikeService`를 아예 호출하지 않아 집계 쿼리도 발생하지 않는다(회귀는 `verifyNoInteractions`로 고정)
- `GET /{quizId}` → 단건 상세. 미제출: answer 계열 키 부재, `submitted:false`(행이 있어도) + **`expired`**(신설, 받았고 시한 지났는지) / 제출: `submitted:true,myOption,correct,answer,liked,likeCount` 포함(제출한 문제일 때만 좋아요 필드도 실린다 — `answer`와 같은 `@JsonInclude(NON_NULL)`). 미존재·**미편성 풀** 모두 404 `QUIZ_NOT_FOUND`
- `POST /{quizId}/submit` `{option}` → 채점 결과 `{correct, answer, myOption, earnedPoint, totalPoint, earnedBq, totalBq}`(7키, 2026-09-03 뒤 2키 신설 — point·bq 두 축 적립 결과, `totalBq`는 `users_bq.bq_score` 누적치). 404·403 `QUIZ_SUBMIT_NOT_ALLOWED`(행이 없거나 미답인데 시한 지남 — `/today` 미경유 또는 8분 경과)·400 `QUIZ_OPTION_NOT_FOUND`(없는 보기, **이미 답한 문제에 없는 보기도 포함** — 2026-08-12부터 이 경우도 400, 종전엔 409였다)·409 `QUIZ_ALREADY_SUBMITTED`(조건부 UPDATE 영향 0행, 동시 race 포함). **검사 순서는 404→403→400→(계정 락·적립)→409 고정** — 순서를 바꾸면 재제출 응답이 갈리는 회귀가 난다
- `GET /submissions?gameId=`(**2026-08-13 전면 교체** — `page` 폐지, `gameId` 필수, 값은 `/today`와 같은 `games.naver_game_id`) → **지목한 경기 한 건**의 이닝별 결산. 없거나 빈 문자열 400, 미매칭 404 `GAME_NOT_FOUND`, `SCHEDULED` 403 `GAME_NOT_STARTED`(종료·취소는 200 — 위 "핵심 클래스" 참고). 응답 `{summary:{correctCount,total,accuracy,earnedPoint,earnedBq}, innings:[{inning,summary:{correctCount,total,accuracy},quizzes:[{quizId,question,type,difficulty,options[{no,text}],myOption,correct,expired,answer,earnedPoint,earnedBq,submittedAt,liked,likeCount}]}]}`(2026-09-03 `earnedBq` 신설 — 경기 전체 `summary`는 5키, 문항 항목은 `earnedPoint` 뒤에 추가. **이닝별 `summary`(`InningSummary`)는 3키 그대로 불변** — 배점 합계는 경기 전체 하나에만 두고, 이닝 합계가 필요하면 FE가 그 이닝 문항들의 `earnedPoint`/`earnedBq`를 더한다) — 이닝 열거·접기 규칙·필드 성질은 전부 위 "핵심 클래스" 항목과 동일
- **`POST /{quizId}/like`(신규) → 좋아요 토글(요청 본문 없음). `{liked, likeCount}`.** 응답의 `liked`가 화면 상태의 정본이다 — **멱등이 아니다**, 같은 요청을 두 번 보내면 원상 복귀한다. ⚠ **이 경로만 404 은닉 규칙이 아니다** — 다른 퀴즈 경로(위 `GET /{quizId}` 등)는 미존재·미편성을 404 `QUIZ_NOT_FOUND`로 감추지만, 여기는 **미존재·미편성·미서빙(아직 못 받음) 셋을 전부 403 `QUIZ_LIKE_NOT_ALLOWED`로 응답해 구분 불가능하게 만든다.** 구현은 퀴즈 조회를 아예 하지 않고 `existsByUserAccount_IdAndQuiz_Id`(=`quiz_users_submit` 행 존재) 확인 하나로 세 경우를 합친다(분기가 하나뿐이라 응답이 갈릴 코드 경로 자체가 없다). ⚠ **2026-08-12 `/today`가 미답 행을 서빙 시점에 만들면서 이 existsBy의 뜻이 "제출했다"에서 "받았다"로 조용히 넓어졌다**(코드 변경 없이 의미만 확장 — `.claude/modules/domain.md` `QuizUserSubmitRepository` 참고) — 지금은 답하지 않고 받기만 한 문제도 좋아요를 누를 수 있다. `QUIZ_LIKE_NOT_ALLOWED` 메시지("좋아요는 직접 푼 문제에만...")와 `quiz-like.md`는 아직 이 확장을 반영하지 않은 **알려진 문구 부채**다(정합 작업은 후속 과제)
- `GET /{quizId}/vote-count` → 아직 답하지 않은 문제의 보기별 투표 수(폴링용). **자격이 없으면 상태 코드를 가르지 않고 200 + `data:null`** — 404·403으로 갈리면 응답 코드만으로 "그 사람이 그 문제를 받았는지"가 드러나고 폴링 화면이 에러 분기를 탄다. 자격 = `quiz_users_submit` 행이 있고 `submit_option_id`가 null(=받았고 아직 미답), **8분 시한은 여기서 안 본다**(시한 지난 미답도 분포는 보여 준다). 보기 목록은 DB에서 오고 Redis에 없는 보기는 0으로 채워, 표가 없거나 Redis가 죽어도 실리는 보기 개수는 늘 같다

## 엔드포인트 — 채팅 (`/rt/chat`)
**전부 응원 구단 단위 폐쇄 공간**(퇴장 제외) — 요청자의 현재 응원 구단과 방의 구단이 달라야 403 `CHATROOM_TEAM_MISMATCH`, 응원 구단이 없으면 400 `SUPPORT_TEAM_REQUIRED`. 판정 순서 404→400→403 고정
- `GET /rooms` → 방 목록(소프트삭제 제외). `teamId`(선택) — 생략하면 응원 구단으로 간주, 응원 구단과 다르면 403. 응답 `{roomUid, team, name}` — participants는 노출하지 않음
- `GET /rooms/{roomUid}` → 방 상세. 없거나 삭제된 방 404, 내 구단 방 아니면 403. 응답 형태는 목록과 동일
- `GET /rooms/{roomUid}/subscribe` → SSE 구독(`text/event-stream`). 표준 `EventSource`는 헤더를 못 실어 인증 실패(401) — fetch 기반 폴리필로 `Authorization` 헤더를 실어야 함. 구단 검사는 연결 시점 1회(스트림 유지 중 재검사 없음). 성립 시 같은 사용자의 기존 구독을 last-one-wins로 축출
- **`DELETE /rooms/{roomUid}/subscribe`(신규) → 명시적 퇴장(구독 종료), 200. 구단 일치 검사를 걸지 않는 전면 멱등**(구독 없어도, 응원 구단 없어도, 방이 없거나 삭제됐어도 200)
- `POST /rooms/{roomUid}/messages` → 전송(`@Valid` content 검증). **저장 전에 욕설 마스킹을 거친다**(2026-09-03) — 저장·응답·SSE가 같은 마스킹 문자열이고 원문은 남지 않으며, 금지어가 있어도 거절 없이 201. `@Size(max=500)`은 원문 기준이라 치환으로 500자를 넘길 수 있는데 자르지 않는다(`chat.content`가 TEXT라 무해). 저장 후 발신자 제외 구독자에게 SSE 전달, 201. 응답 `MessageResponse`·SSE payload `MessageEvent` 둘 다 **2026-08-20부터 `profileImgUrl` 포함**(발신자 `users_account.profile_img_url` 그대로, BaseURL 없는 EP — `user` 모듈 `GET /api/users/me`와 같은 형태·같은 값 규약). 발신자 계정이 이미 로딩돼 있어 추가 SELECT 없음. SSE에도 함께 싣는 이유는 히스토리에만 실으면 방금 도착한 메시지만 아바타가 비었다가 새로고침해야 채워지기 때문
- `GET /rooms/{roomUid}/messages?page=` → 히스토리(최신순 30건 페이징, blind·삭제 제외). 항목마다 `profileImgUrl` 포함(위와 동일). 탈퇴자 메시지는 `(알수없음)` 더미 계정으로 이관되고(`ChatRepository.reassignSender`) 그 계정은 프로필이 없어 자연히 `null` — 별도 분기 없음
- `POST /rooms/{roomUid}/messages/{messageId}/report` → 신고 → 즉시 blind(멱등). 자기신고 403, 삭제 메시지 404
