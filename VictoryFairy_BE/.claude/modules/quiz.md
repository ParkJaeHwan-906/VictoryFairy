# quiz 모듈

> quiz 작업 시에만 로드되는 슬림 컨텍스트. (공통: `com.skhynix` 독립 앱, `:common`=ApiResponse/BusinessException/ErrorCode, `:domain`=엔티티/리포지토리, MySQL+spring-dotenv, prod `ddl-auto`는 앱마다 다름 — user=`update`, quiz=`none`)

## 책임
Quiz 도메인 REST API 서버. **구단별 채팅 기능 구현 완료**: `chat`(방 목록/상세·구독·퇴장·전송·히스토리·신고 REST+SSE) + `realtime`(SSE 실시간 전달). **채팅방은 응원 구단 단위 폐쇄 공간**(목록·방 단위 경로 전부 구단 가드) **+ 서버 주도 구독 종료**(명시적 퇴장, 중복 구독 last-one-wins 축출). **퀴즈 기능**: `quiz`(S3 quiz-candidates → RDB 적재 + 매일 편성(전원 동일 데일리 세트) + 조회·개별 조회·제출(채점/포인트 적립)·풀이 이력·좋아요 토글 API). **포트 8081.**

## 핵심 클래스 (`quiz/src/main/java/com/skhynix/quiz/`)
- `QuizApplication` — 메인 진입점. `scanBasePackages = "com.skhynix.quiz"`로 **좁게** 스캔 (user는 `com.skhynix` 전체). `@EntityScan`/`@EnableJpaRepositories`만 `com.skhynix` 전역.
- `SecurityConfig` — stateless, `@Import({JwtVerificationConfig.class, GlobalExceptionHandler.class})`로 `web-support`의 JWT 검증 부품 + 예외 어드바이스를 명시적으로 끌어옴(좁은 스캔이 `com.skhynix.websupport.*`를 놓쳐 자동 감지 안 됨). `securityFilterChain`이 `JwtAuthenticationFilter`를 직접 `new`로 생성하며 `UserAccountRepository`(`:domain`, uid→id 조회)도 함께 넘김 — `web-support`의 필터 생성자가 바뀌면 여기도 같이 고쳐야 함. `/`, `/error`, `GET /health` 외 전부 인증 필수. 미인증 401도 `web-support`의 `RestAuthenticationEntryPoint`를 그대로 import해 등록(동일 커플링 — 생성자 바뀌면 같이 고칠 것)
- `chat/controller/ChatController` — `/rt/chat/**` REST+SSE. principal은 `@AuthenticationPrincipal Long userAccountId`(`JwtAuthenticationFilter`가 주입). `DELETE /rooms/{roomUid}/subscribe`(명시적 퇴장)도 이 인증 규칙에 자연히 걸림(SecurityConfig 수정 불필요)
- `chat/service/ChatService` — 방 조회/구독/퇴장/전송/히스토리/신고 로직. **채팅방은 응원 구단 단위 폐쇄 공간**: 목록·방 단위 경로 전부 요청자의 현재 응원 구단(`user_support_team.oppose is null`)과 방의 구단이 같아야 하고, 판정 순서는 **404(방 존재) → 400(`SUPPORT_TEAM_REQUIRED`, 응원 구단 없음) → 403(`CHATROOM_TEAM_MISMATCH`, 구단 불일치)로 고정**이다. `unsubscribe()`(퇴장)만 예외 — **가드를 걸지 않고 전면 멱등**이다(구단 일치도, 응원 구단 존재도, 방 존재·비삭제도 검사 안 함 — 정리 요청을 막으면 구단을 바꾼 사용자가 낡은 연결을 못 닫는다). 전송 성공 후 SSE 발행은 fire-and-forget(예외 삼킴, 저장·응답은 되돌리지 않음). 구독 성립·퇴장 시 종료 명령도 같은 커밋-후-발행 경로를 탄다
- `realtime/RealtimeEventPublisher` — 실시간 전송 포트(토픽=roomUid). **quiz 정답 집계 등 향후 기능도 재사용할 일반 설계**. 구현은 프로파일로 갈린다: `prod`=`RedisPubSubPublisher`(단일 채널 `realtime:events` 로 발행) + `RealtimeEventSubscriber`/`RealtimeRedisConfig`(리스너 컨테이너가 전 파드에서 수신 → 자기 레지스트리로 전달), `!prod`=`InMemoryPublisher`. 발행 파드도 자기 구독으로 되받으므로 Redis 구현은 로컬 레지스트리로 직접 전달하지 않는다(이중 전달 방지 — 테스트로 고정). quiz-app HPA maxReplicas=4 이므로 이 경로가 없으면 스케일아웃 시 메시지가 조용히 유실된다. **버스에는 전송 이벤트 외에 제어 신호 `subscription-close`(`SubscriptionCloseCommand`)도 실린다** — 양쪽 수신 측(`InMemoryPublisher.publish`/`RealtimeEventSubscriber.onMessage`) 모두 `SubscriptionCloseCommand.isCloseSignal(event)`로 전송(`registry.publish`)과 종료(`registry.handleCloseCommand`)를 분기한다. 분기를 빠뜨리면 종료 명령이 구독자에게 `data:`로 새어 나간다. `originInstanceId`(발행한 `SseEmitterRegistry.instanceId()`)로 발행 파드가 되받은 자기 명령을 무시한다 — 없으면 방금 연 새 구독이 자기 축출 명령에 끊긴다
- **이 앱은 시드를 넣지 않는다.** `spring.sql.init` 배선도, `build.gradle` 의 `processResources` 복사도 없다(실측: `quiz/build/resources/main/` 에 `sql/` 디렉터리 자체가 없음). 기본 데이터(구단 10개·SYSTEM 계정·구단별 채팅방 10개·경기 상태 5행·퀴즈 유형 2행)는 전부 **`user` 앱이 dev·prod 기동 시** `infra/sql` 의 시드 4종으로 채운다 — 테이블을 만드는 앱과 채우는 앱을 하나로 모은 결과다(`.claude/modules/domain.md` 참고).
  ⚠ **빈 DB 에 `:quiz:bootRun` 만 하면 스키마는 서지만 데이터가 비어 있다.** `@EntityScan("com.skhynix")` + dev `ddl-auto=update` 라 domain 엔티티 전체(2026-08-07 기준 22테이블)가 생기지만 시드는 0행이라, 채팅방 목록이 비거나 첫 출제가 `quiz_type` FK 위반으로 실패한다. 설정을 의심하기 전에 **`:user:bootRun` 을 한 번 띄울 것.** (테이블 수는 domain 엔티티가 늘 때마다 바뀌니 판정 근거로 쓰지 말 것.)
- `realtime/SseEmitterRegistry` — 방별 SSE 구독 관리(발신자 제외 fan-out), 죽은 연결을 하트비트로 회수. 타임아웃 30분·하트비트 15초(`:ping` 주석 프레임). `register()`는 `rooms.compute(...)`로, `remove()`는 `rooms.computeIfPresent(...)`로 구현되어 있다 — Set에 넣고 빼는 일과 빈 Set을 맵에서 걷어내는 일을 같은 빈(bin) 잠금 아래 원자적으로 묶기 위함. **`computeIfAbsent`+람다 바깥 `add`로 "단순화"하면 고아 Set 레이스가 재발한다**: 마지막 퇴장(Set 비어 맵에서 제거)과 신규 입장(같은 Set을 얻어 add)이 겹치면 새 구독이 맵에서 떨어져 나간 Set에 갇혀 fan-out·하트비트 순회에서 누락된다(해당 사용자는 메시지를 못 받음). `count(roomUid)`는 남아 있으나 프로덕션 호출부는 없음(테스트·진단용 접근자). **참여 인원(participants)은 어디에도 서빙되지 않는다** — 인메모리 구독 수는 파드별 값이라 다중 파드에서 부정확하고, DB 컬럼 집계는 connect/disconnect마다 write가 폭주해 RDB 집계+Redis 재계산까지 구현했다가 방향 전환으로 전부 롤백했다(제품 결정). `Chatroom.participants`/`join()`/`leave()`는 되살릴 여지를 남기려는 의도적 결정으로 domain에 남아 있으나 quiz는 미사용
  - **서버 주도 종료가 신설됐다**: `closeSubscriptions(roomUid, userAccountId)`(그 방만, 명시적 퇴장) · `closeAllSubscriptions(userAccountId)`(방 무관 전부, 축출의 원격 처리분) · `handleCloseCommand(roomUid, command)`(버스로 받은 종료 명령 처리 — `command.originInstanceId()`가 자기 `instanceId()`와 같으면 무시). `instanceId()`(인스턴스 식별용 랜덤 UUID)를 종료 명령에 실어 발행 파드가 되받은 자기 명령을 무시하게 한다
  - `register()`가 **last-one-wins 축출**을 한다 — 같은 사용자의 기존 구독을 방 불문 전부 끊고 새 구독만 남긴다(**멀티탭이 사실상 금지된다**: 같은 계정 두 탭이면 먼저 연 탭이 끊긴다). **`emitter.complete()`는 반드시 `compute`/`computeIfPresent` 람다 밖에서 불러야 한다** — `complete()`가 태우는 `onCompletion` 콜백이 `remove()`로 같은 맵을 재귀 갱신해 `ConcurrentHashMap`의 재귀 갱신 금지 계약을 깬다. 축출 구현(등록과 기존 연결 제거를 한 흐름에 묶는 지점)이 위 고아 Set 레이스 픽스를 가장 깨뜨리기 쉬운 자리다 — `compute` 바깥에서 remove 후 add 하는 형태로 풀면 그 회귀 테스트(AC-CHAT-11-5·55-2)가 다시 깨진다
- `realtime/RealtimeSchedulingConfig` — `@EnableScheduling`으로 하트비트 구동(quiz 좁은 스캔 범위 안이라 자동 등록). **`quiz/ingest`의 `@Scheduled`(일일 적재)도 이 활성화에 얹혀 돈다**
- `quiz/ingest/*` — **S3 → RDB 퀴즈 적재**. `QuizCandidate`(스펙 4.3 계약 record — evidence·settlement 등 저장 안 하는 필드는 일부러 안 받음, Jackson 3 기본이 모르는 필드 무시), `QuizCandidateReader`(`quiz-candidates/{date}/` 읽기 전용, 파일 단위 실패 격리), `QuizIngestService`(후보당 1트랜잭션 — KNOWLEDGE만 적재·PREDICTION 스킵, format→quiz_type 이름 매핑(OX→`O/X`, BINARY/MULTI4→`객관식`), answer A→0 번호 변환, subject→FK 해석. **정답 유출 방지 규칙**: subject는 문제가 '전제'하는 엔티티만 담겨 오므로 로더가 `player.getTeam()` 등으로 보강하면 안 됨. 예외: game 해석 성공 시 홈=team·원정=opponentTeam 채움. 해석 실패는 해당 FK만 null), `QuizIngestScheduler`(cron 10:30 KST + 최근 3일 catch-up — 루틴이 08:50+60분 상한이라 30분 여유. **분산 락 없음(의도)**: `uk_quizzes_external_id` UNIQUE가 파드 동시 실행의 심판이고 위반은 "이미 적재됨"으로 삼킴. **적재 후 오늘만 `publishDaily` 호출** — 과거 날짜 편성 금지, 지난 세트는 동결), `QuizIngestStartupRunner`(기동 시 1회 — 10:30 이후 재시작한 파드의 사각 메움, 실패해도 기동 계속)
  - **`quiz_date` = 출제일(생성일 아님), NULL = 미편성 풀.** 적재 시 게임 귀속 후보(naverGameId 명시 — game FK 해석 실패여도)만 파티션 날짜를 스탬프하고, 나머지(역대기록형 등 시효성 없음)는 NULL 풀에 쌓는다. 스테일한 "오늘 경기" 문구가 풀에서 나중에 튀어나오는 것을 막는 규칙
- `quiz/service/QuizPublishService` — **매일 편성**: 그날 세트가 `quiz.serve.daily-count`(기본 10)에 못 미치면 풀에서 부족분만 `UPDATE ... WHERE quiz_date IS NULL ORDER BY id ASC LIMIT`(네이티브)로 스탬프. id ASC = 오래된 것부터 결정적 선택(파드 간 선택 안 갈림). 멀티 파드 동시 실행 시 최대 2배 과편성 가능하나 **허용**(세트는 여전히 전원 동일, 락 비용 > 무해한 결과). **전원 동일 데일리 세트가 설계 원칙**(레이팅 공정성 — 같은 문제·같은 타이밍이어야 점수 비교 가능)
- `quiz/controller/QuizController`·`quiz/service/QuizService` — `GET /rt/quizzes/today`(**`gameId` 필수** + 선호 정렬 + `preferredOnly` 필터)·`GET /rt/quizzes/{id}`(단건 상세). '오늘'은 `kstClock`(KST 고정 — 파드 JVM UTC라 기본 클록이면 자정~09시 하루 어긋남). 보기는 `quiz_id IN` 2쿼리 방식(N+1 금지 — `QuizOptionRepository` javadoc). **선호(preferred) = 내 응원 구단이 문제의 대상·상대 구단이거나 대상 선수가 내 응원 선수** — 판정은 메모리에서(세트가 십수 건), 대상 FK는 목록 `@EntityGraph`(quizType·team·opponentTeam·player·game)가 실어 와 LAZY 초기화 없음. **각 선호 그룹 안 정렬은 id ASC 가 아니라 사용자별 고정 랜덤**(`shuffleKey(userAccountId, quizId)` — 문제 단위 splitmix64 순수 산술, 상태·DB 없이 같은 사용자·같은 문제는 항상 같은 키. 키 충돌 시 id ASC로 tie-break). `Collections.shuffle`·`Random`/`ThreadLocalRandom`은 의도적으로 배제(아래 주의 참고). **preferredOnly의 "응원 정보가 없으면 no-op(전체 반환)" 분기는 2026-08-12부터 도달 불가능한 죽은 코드다** — `gameId` 검증이 응원 구단 없는 계정을 먼저 403으로 막아, 이 필터에 도달하는 시점엔 응원 구단이 항상 있다. **`/today` 응답은 `quiz.serve.max-today-count`(기본 20)로 상한** — 정렬·필터가 다 끝난 목록을 앞에서 자르는 연산이어야 기존 부분집합 안정성 테스트가 안 깨진다(실측: devdb 오늘 세트 33건에서 상한이 실제로 발동해 20건 반환). **미편성 풀 문제는 단건 조회도 404**(id 순회로 내일 출제분 미리보기 차단). 미제출 상세엔 `answer` 키 자체가 없다(`QuizDetailResponse` `@JsonInclude(NON_NULL)`, 테스트로 고정) — 제출 후엔 myOption/correct/answer 포함(복기)
- **`/today`는 쓰기 경로다**(`@Transactional`이고 `readOnly`가 아니다): 응답에 실은 문제마다 `quiz_users_submit`에 미답 행을 만드는 것 자체가 제출 자격이 된다 — **Redis 제출 티켓은 전면 폐기됐다**(`QuizSubmissionTicketStore` 삭제, 아래 "의존"·"주의" 참고). 왕복은 문제 수와 무관하게 **네이티브 단일 INSERT 1회**(`QuizUserSubmitRepositoryImpl.insertUnansweredRows`, `.claude/modules/domain.md` 참고), 이미 행이 있는 문제는 손대지 않아 **같은 세트를 다시 받는 재호출은 쓰기 0건**이다.
- **`/today` 재설계(2026-08-12 5차, 계약 `docs/requirements/quiz/quiz-inning-tracking.md`) — 세트를 줄지부터 가리는 관문이 통째로 새로 생겼다.** 검증 순서는 ① `servableGame`(경기 해석·검증 4종: 존재·오늘(KST)·요청자 응원 구단 참여·`IN_PROGRESS` — 하나라도 아니면 403 `QUIZ_NOT_SERVABLE`, 사유 비공개) ② `servableInning`(`current_inning` 읽기 — NULL 이면 같은 403, "이닝을 못 구하면 안 준다"는 방어) ③ `existsByUserAccount_IdAndGame_IdAndInning`(그 이닝에 이미 받았으면 409 `QUIZ_ALREADY_SERVED_IN_INNING`)이고, 통과한 뒤에야 "무엇을 줄지"를 고른다. **이닝의 원천이 바뀌었다** — "문제가 귀속된 경기"(`quizzes.game_id`)가 아니라 **"요청자가 지목한 경기"**(`gameId` 파라미터, 값은 내부 PK가 아니라 `games.naver_game_id`)다. 한 요청으로 만들어지는 행은 문제와 무관하게 전부 같은 `(game_id, inning)`을 갖는다 — `quizzes.game_id`는 적재·선호 판정에는 계속 쓰이지만 이닝 판정에서는 완전히 빠졌다. **응원 구단의 역할도 바뀌었다** — 서버가 경기를 찾는 근거가 아니라 FE 가 지목한 경기를 검증하는 기준이다. **경기 상태 판정은 `game_statuses`의 id 가 아니라 `name` 문자열**로 한다(시드가 이름 기준 upsert 라 id 가 환경마다 다를 수 있음).
- **재조회가 폐지됐다 — 종전(3차) 계약의 정반대다.** 3차는 "미답이고 시한이 남은 문제는 계속 서빙한다"(재조회로 세트를 지킴)였으나, **5차는 목록 제외 기준을 "행이 있는가" 하나로 좁혔다**(`findServedQuizIds`) — 행이 있는 문제는 답 여부·시한과 무관하게 전부 제외되고, 안 푼 문제는 미제출(오답)로 확정된다. 새로고침·앱 복귀 한 번에 그 이닝 세트를 잃는다는 뜻이며 **알고 수용한 결과**다(받은 문제의 제출은 8분 안엔 그대로 가능 — 잃는 것은 문제 본문 재수신뿐). **8분 시한은 서빙 판정에서 완전히 빠지고 제출 경로(`QuizSubmitWindow`)에만 남는다.** 상한(20)에 잘려 나간 문제는 행이 안 생겨 그 제출도 403이다. 상세의 `submitted`는 **행이 아니라 답의 존재**가 기준이고(안 그러면 미답 행에 정답이 실린다), `expired`가 "받았고 시한 지남"을 구분한다
- `quiz/controller/QuizSubmissionController`·`quiz/service/QuizSubmitService` — `POST /rt/quizzes/{id}/submit`(제출·채점) + `GET /rt/quizzes/submissions?gameId=`(**2026-08-13 전면 교체** — 계약 `docs/requirements/quiz/quiz-submission-by-inning.md`, 승인됨). **제출은 INSERT가 아니라 조건부 UPDATE다**(`QuizUserSubmitRepository.fillAnswer` — `submitOption is null AND createdAt >= 시한하한`) — 영향 행 0이 곧 중복 제출 판정이라 종전의 `existsBy` 선검사 + UNIQUE 위반 변환 이중 구조가 사라졌다. **검사 순서는 404(미존재·미편성 은닉)→403(`QUIZ_SUBMIT_NOT_ALLOWED`, 제출 자격 없음 — 행이 없거나 미답인데 시한 지남)→400(없는 보기)→계정 행 비관적 락(`findWithLockById`)+`addPoint` 적립→409(`fillAnswer` 영향 0행, `QUIZ_ALREADY_SUBMITTED`)**. 종전(…409→403…)과 순서가 뒤집혔고, **관측 가능한 변화 하나** — 이미 답한 문제에 없는 보기 번호를 보내면 종전 409였고 **이제 400**이다(중복 판정이 선검사가 아니라 UPDATE 결과로만 나오기 때문). **제출 자격의 근거는 DB 행이지 Redis 티켓이 아니다** — 이 경로는 이제 Redis 장애와 무관하다. 이닝은 제출 시점에 건드리지 않는다(`/today`가 서빙 시점에 이미 찍어 둔 값을 그대로 두고 `games`를 다시 읽지 않음). 403 거절은 행·포인트·락 변경 없이 흔적을 0으로 남겨 다음 `/today`에 재출제된다. **bq_score는 안 건드림**(레이팅 설계 확정 전)
- `GET /submissions`는 **조회 단위가 계정 전체에서 경기 하나로 좁아졌다** — `page` 폐지, **`gameId` 필수**(값은 `/today`와 같은 축, `games.naver_game_id` 문자열). 검사 순서는 **404(`GAME_NOT_FOUND`) → 403(`GAME_NOT_STARTED`, `SCHEDULED` 경기) → 200 고정**이고, **`/today`의 servable 4종 검증(존재·오늘(KST)·응원 구단 참여·`IN_PROGRESS`)은 이 경로에 적용하지 않는다** — 종료·취소 경기가 200인 것이 이 기능의 목적이라(끝난 경기를 결산하는 화면), 같은 `gameId` 파라미터를 받는 두 경로(`/today`·`/submissions`)의 검증 기준이 서로 다르다는 뜻이고 혼동하기 쉬운 지점이다. `CANCELED`도 200(노게임이면 진행된 이닝의 기록이 실제로 남아 있어 접으면 사용자가 자기 기록을 잃는다) — 403은 `SCHEDULED` 하나뿐이다. 응답이 페이징 구조에서 **`summary`(경기 전체) + `innings[]`(이닝별 `summary` + 문제 리스트)** 로 통째로 바뀌었고, 문제 항목엔 보기 배열 `options` 신설, `quizDate`·`myOptionText`·`answerText`는 삭제(`options`가 흡수), `liked`/`likeCount`는 그대로 유지. **이닝 열거는 경기 상태(`game_statuses.name`)가 1차 축이고 두 이닝 컬럼(`current_inning`/`last_inning`)의 폴백은 금지**: `IN_PROGRESS` → `1..current_inning-1`(현재 이닝 제외, 1회면 빈 배열) / `FINISHED`·`DRAW`·`CANCELED` → `1..last_inning` / 표에 없는 미지 상태 → `FINISHED` 계열 취급 / 읽어야 할 컬럼이 NULL이면 200 + 빈 배열(에러 아님 — 원천이 py-collector라 이 앱이 통제 못 하는 결손). **접기 규칙은 두 단위로 갈린다**: 그 경기에 내 행이 0건이면 열거 범위가 계산돼도 `innings: []`로 통째로 접히고(경기 단위), 접히지 않으면 범위의 모든 이닝이 원소로 남아 빈 이닝도 `quizzes: []` + `0/0`으로 실린다(이닝 단위는 안 접는다). ⚠ **`innings: []`가 세 사실(그 경기 기록 0건·이닝 값 NULL·1회 진행 중)을 한 모양으로 덮어 응답만으로 구별 불가**하다 — 사유 필드 없음(알고 택한 제약, 구별 필요해지면 후속 과제). **계정 누적 정답률(계정 전체 합산 total/correctCount/accuracy)이 이 엔드포인트에서 사라졌다** — 대체 엔드포인트는 이번 범위 밖, 마이페이지 등 그 값을 쓰던 소비처가 있으면 후속 과제. `earnedPoint`는 정답 행의 `quizzes.score` 합(적립 원장이 아니라 표시용 근사치, `score` NULL은 0). 조회는 `findGameSubmissions`(`s.game.id` 등치, `submitOption`만 left join fetch — inner join이면 미답 행이 빠져 이닝별 정답률이 부풀려진다) 1건 + 보기 `quiz_id IN` 1건 + 좋아요 2건으로 **이닝·문항 수와 무관하게 SQL 상수**다. `myOption`/`submittedAt` 등 필드 성질은 종전과 동일(`submittedAt`은 `updated_at`, 미답이면 `myOption` null·`expired`로 진행 중/시한초과 구분)
- `quiz/service/QuizLikeService`(파사드) ↔ package-private `quiz/service/QuizLikeToggler`(트랜잭션 단위) — **quiz 서비스 계층 최초로 파사드/트랜잭션 클래스를 분리한 패턴**(신설 2026-08-11). `POST /{quizId}/like`를 처리하며 이유는 순전히 트랜잭션 경계다: `uk_quizzes_like_account_quiz` UNIQUE 충돌(동시에 첫 좋아요 2건)을 정상 응답으로 흡수하려면 확정 상태 재조회가 **새 트랜잭션**이어야 하는데, 같은 클래스 self-invocation은 프록시를 안 지나 새 트랜잭션이 안 열리고 롤백 표시된 트랜잭션에서 재조회하면 `UnexpectedRollbackException`(500)이 난다. **두 클래스를 하나로 합치면 그 자리에서 500으로 회귀한다** — 합치자는 "단순화" 제안은 거절할 것. `QuizLikeService`는 상세·이력의 좋아요 상태 조립(`likeOf`/`likesOf`, 항목 수와 무관하게 조회 2건 — 집계 `countLikesByQuizIds` + 내 좋아요 `findLikedQuizIds`)도 겸한다. 계약 원본은 `docs/requirements/quiz/quiz-like.md`(승인됨 2026-08-11)

## 엔드포인트 — 퀴즈 (`/rt/quizzes`) — 전부 인증 필수
- `GET /today?gameId=&preferredOnly=` → **`gameId` 필수**(값은 내부 PK 가 아니라 `games.naver_game_id` 문자열 — `GameResponse.gameId`로 이미 노출된 그 값). 지목된 경기가 존재·오늘(KST)·요청자의 응원 구단 참여·`IN_PROGRESS` 4종을 통과하고 그 이닝에 아직 안 받았어야 세트를 준다 — 하나라도 아니면 403 `QUIZ_NOT_SERVABLE`, 그 이닝에 이미 받았으면 409 `QUIZ_ALREADY_SERVED_IN_INNING`. 통과하면 오늘(KST) 세트 중 **행이 없는(=아직 안 받은) 문제만**(재조회 없음 — 아래 "재조회 폐지" 참고) **선호 먼저·그 안에서 사용자별 고정 랜덤**(전 사용자 동일 순서 아님 — 앞쪽 문제로 제출 쏠림 방지). `{id, type(객관식|O/X), question, difficulty, point, preferred, options[{no,text}]}` — **정답 미포함**. 빈 배열 = **줄 수 있는데 줄 게 없다**(오늘 세트 없음 · 남은 문제를 이미 다 받음)는 뜻이고, "지금은 줄 수 없다"는 전부 에러(403/409)다. **응답 개수 상한 20**(`quiz.serve.max-today-count`)이고, 실린 문제마다 `quiz_users_submit`에 미답 행이 생기는 것 자체가 제출 자격이다(**Redis 제출 티켓은 폐기됨**) — 상한에 잘려 나간 문제는 행이 안 생겨 제출도 403이다. **좋아요 필드는 안 실린다** — 이 목록의 항목은 정의상 전부 미제출이라 전원 좋아요 불가, `QuizLikeService`를 아예 호출하지 않아 집계 쿼리도 발생하지 않는다(회귀는 `verifyNoInteractions`로 고정)

- `GET /submissions?gameId=`(**2026-08-13 전면 교체** — `page` 폐지, `gameId` 필수, 값은 `/today`와 같은 `games.naver_game_id`) → **지목한 경기 한 건**의 이닝별 결산. 없거나 빈 문자열 400, 미매칭 404 `GAME_NOT_FOUND`, `SCHEDULED` 403 `GAME_NOT_STARTED`(종료·취소는 200 — 위 "핵심 클래스" 참고). 응답 `{summary:{correctCount,total,accuracy,earnedPoint}, innings:[{inning,summary:{correctCount,total,accuracy},quizzes:[{quizId,question,type,difficulty,options[{no,text}],myOption,correct,expired,answer,earnedPoint,submittedAt,liked,likeCount}]}]}` — 이닝 열거·접기 규칙·필드 성질은 전부 위 "핵심 클래스" 항목과 동일

- **`DELETE /rooms/{roomUid}/subscribe`(신규) → 명시적 퇴장(구독 종료), 200. 구단 일치 검사를 걸지 않는 전면 멱등**(구독 없어도, 응원 구단 없어도, 방이 없거나 삭제됐어도 200)
- `POST /rooms/{roomUid}/messages` → 전송(`@Valid` content 검증). 저장 후 발신자 제외 구독자에게 SSE 전달, 201
- `GET /rooms/{roomUid}/messages?page=` → 히스토리(최신순 30건 페이징, blind·삭제 제외)
- `POST /rooms/{roomUid}/messages/{messageId}/report` → 신고 → 즉시 blind(멱등). 자기신고 403, 삭제 메시지 404

  - 파드 간 전파(Redis 경로)는 dev 프로파일에서 검증 불가다 — `InMemoryPublisher`가 그 자리를 대신하므로, 확인하려면 prod 프로파일 인스턴스를 2개 띄워야 한다
- **docker 실측(2026-08-12) — Redis 배선은 실증됐다**: 로컬 compose 는 user·quiz 에 `SPRING_DATA_REDIS_HOST=redis`/`SPRING_DATA_REDIS_PORT=6379` 만 주입하고 `REDIS_HOST` 는 아예 없다. yaml 의 `${REDIS_HOST:localhost}` 와 이름이 달라 보이지만 **Spring relaxed binding 이 OS 환경변수를 우선 적용해 플레이스홀더 해석 자체가 일어나지 않는다** — redis 컨테이너에서 `MONITOR` 를 걸고 quiz 의 `/rt/actuator/health` 를 호출해 quiz 컨테이너 IP 에서 `INFO server` 가 도달하는 것으로 확정했다(정적 추론이 아니라 실측). 같은 방식으로 **`/rt/actuator/health/readiness` 호출 시엔 redis 에 아무 커맨드도 가지 않음**을 확인 — readiness 그룹이 redis 를 안 본다는 k8s probe 계약이 그대로 유지된다. ⚠ `show-details` 가 없어(기본 `never`) 응답 본문에는 컴포넌트별 상태가 안 나온다 — 인디케이터 동작 확인은 body 가 아니라 MONITOR 트래픽으로 해야 한다
- **`/today` 재설계 검증(devdb 실기동 + docker 컨테이너, 2026-08-12) — 3차(미답 행 서빙·조건부 UPDATE)·5차(`gameId`·회차 제한) 모두 PASS, 종전 "로컬 통합 검증 구조적 공백"은 닫혔다**:
  - devdb 실기동(`:quiz:bootRun`, 3차): `/today` 두 번 호출 시 목록 일치·20튜플 단일 INSERT·재호출 쓰기 0건, 제출이 같은 행 UPDATE, 재제출 409, `/today` 미경유 403, 시한 초과 403, 답한 문제+없는 보기 400, 동시 5회 호출에도 중복 행 0, Redis 연결 로그 전무(제출 경로가 Redis와 완전히 무관함을 실측으로 확정)
  - docker(3차): **마이그레이션 미적용 상태에서 `GET /today`가 실제로 500(`Column 'submit_option_id' cannot be null`)**인 것을 재현한 뒤 `infra/sql/migrate-quiz-submit-nullable.sql` 적용 후 정상화, 컨테이너에서 제출 라이프사이클(200/409/403)까지 실증
  - docker(5차): **`infra/sql/migrate-quiz-submit-game.sql` 적용도 quiz 배포의 선행 조건이다** — 미적용 시 `GET /today`가 500(`Unknown column 'qus1_0.game_id'`, 공통 예외 래퍼도 못 타는 순수 스프링 500), 적용 후 **재시작 없이** 200 정상화(커넥션 풀이 스키마 변경을 그때그때 반영). 이미지 빌드·prod 프로파일 기동·400(파라미터 누락)/200/409/403·제출 라이프사이클까지 PASS. ⚠ **`deploy-eks.yml`에는 이 SQL 적용 단계가 없다** — 두 마이그레이션 다 워크플로에 없는 수동 적용 대상이라 빠뜨리면 prod `/today`가 통째로 500

  - 남은 한계: EKS ALB·TLS·Ingress 경로는 로컬에 없다. **`current_inning` 원천은 py-collector 에 구현되어 있다**(`kbo_collector/game_records.py` `parse_inning` 이 `statusInfo` 에서 뽑고 — detail API 의 `currentInning` 이 아니다 — `db.py` 의 upsert 가 `current_inning=VALUES(current_inning)` 로 매번 덮어쓴다). **값이 있는 구간은 경기가 `IN_PROGRESS` 일 때뿐이고, 시작 전·종료 후에는 NULL 이다**(사용자 확인) — 즉 `IN_PROGRESS` 검사와 `servableInning` 의 NULL 방어는 같은 불변식의 양면이며, 후자는 그 불변식을 **원천이 소유**하기 때문에 두는 방어다. 로컬·devdb 에서 이닝이 비어 있는 것은 그 환경에 수집기가 안 돌기 때문이고, 그때는 값을 수동으로 넣어야 `/today` 가 200 이 된다. devdb 의 SYSTEM 계정(`users_account.id=2`)에 검증 흔적(제출 기록·point 적립)이 남아 있다 — 공유 devdb 의 테스트 부산물
